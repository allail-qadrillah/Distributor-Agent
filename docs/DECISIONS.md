# Decisions

## 2026-11-19 (Phase 4, WhatsApp bridge, working tree, uncommitted)

- Bridge is transport only. `services/whatsapp-bridge/` (Node 26 ESM) moves WhatsApp traffic and owns no business rule, no database, no broker. Single runtime dependency: `@whiskeysockets/baileys` pinned exactly 6.7.24 (no fork, no patch). The QR encoder is in-repo (`src/qr.js`, ISO/IEC 18004 byte mode, levels L/M) because the approved dependency list has no QR package. `qrcode` is a devDependency used only as a test oracle.
- The Phase 3 wire contract is preserved exactly. The only approved change (spec §5): duplicate inbound (same conversation, external message id already stored) answers `mark_read` computed from the stored message status, so a redelivered unread message still earns a receipt. No new migration, no new table.
- Inbound durability: the socket listener persists every raw event synchronously (temp file, fsync, atomic rename, dir fsync) before splitting it into one record per message. Records are keyed `msg-<sha256(full message key incl. participant)>`, and dedup checks retry/processing/quarantine. The raw event file is deleted only after the split succeeds (see the startup re-split bullet below) so the capacity guard can observe drain. Crash recovery on start returns `processing/` records to `retry/` and re-splits leftover raw events (idempotent).
- Split-time quarantine (review remediation, same working tree): a `notify` message whose key has no usable `remoteJid` (missing, non-object, non-string, or empty) is quarantined at split time instead of dropped. The record keeps reason `no_usable_jid`, jid null, the full original WAMessage payload, and id = sha256 of the canonical full message (no key exists to hash), deduplicated by the same `_existsAnywhere` check. It never enters `retry/`, is never claimable, and occupies no JID slot. `splitEvent` returns `{ created, skipped, quarantined, dropped }`, with `dropped` remaining only for history-sync `append` events. The persist-then-split event sequence is unchanged, so crash recovery preserves quarantined records too.
- Inbound scheduling (review remediation, same working tree): `claimNext` computes each JID's earliest record in `retry/` (its head). A head whose `availableAt` is in the future blocks its whole JID and still counts toward the `maxJids` ceiling (default 5). An in-flight (`processing/`) JID blocks its JID as before. A record is claimed only when it is its JID's unblocked head and a slot is free. One waiting JID never blocks the global queue, so unrelated JIDs keep progressing. Backoff values, the 5-JID ceiling, and the directory layout are unchanged.
- Startup re-split data safety (second review remediation, same working tree): `resplitAll()` deletes a raw event only after its split succeeds. Only unparseable event content is `inbound_event_corrupt` (warned and dropped, the pre-existing policy); a read failure or a record write failure (ENOSPC, EACCES, EIO, ...) propagates, so startup fails loudly (`bridge_start_failed`) and the raw event stays in `incoming/` for the next attempt, where the idempotent full-key dedup completes the split without duplicating already-written records. This matches `ingest()` and `recoverProcessing()`, which never delete after a failed write.
- `no_usable_jid` recovery (second review remediation, same working tree): the generic move-to-`retry/` is unsafe for a `no_usable_jid` record. An uncorrected keyless message is delivered, Python answers 200 `skipped:invalid_event_shape`, and the bridge deletes the record as done, silently losing it. The documented operator procedure (bridge README, "Quarantine recovery"): identify by `quarantineReason`, inspect the preserved `message`, establish the true key from a trusted source (never invented or guessed), correct `message.key` plus the record's own `key` and `jid`, verify `remoteJid`/`id`/`fromMe`, and only then move to `retry/`; otherwise the record stays quarantined. No Python normalization or Phase 3 contract change.
- Forwarder retry policy: 2xx → done, with the read receipt via `readMessages` BEFORE markDone (a receipt failure retries the record, and Python dedups the redelivery). 429 → honor `Retry-After`, else backoff. 400/422 → `quarantine/` (manual recovery: move the file back to `retry/`; a `no_usable_jid` record needs key correction first, see the bullet above). 401/403/404/405 → global pause until restart. 5xx/timeout/network → exponential backoff capped at 5 min. One message per webhook request, claimed by the inbound scheduling rule above.
- Outbound: preallocate a Baileys message id, then persist `outbound/<messageId>.json` (messageId → outbox_id) BEFORE `sendMessage`. Confirmed-not-sent errors delete the mapping and answer 200 `failed` (retryable, matching Phase 3 adapter semantics). A send timeout keeps the mapping and answers 500 `unknown` (never auto-resent, reconciled only by a later delivery report). Single-flight gate: one send in flight, at most 10 waiting, past that 429. During shutdown, new requests get 200 `failed`/`shutting_down` (confirmed not sent).
- Receipts: only `fromMe` updates classify. ERROR(0) → `failed`. DELIVERY_ACK/READ/PLAYED(3/4/5) → `delivered`. PENDING/SERVER_ACK(1/2) and unrecognized values hold the mapping: an ambiguous receipt is never reported as failed or unknown. Delivery reports retry until 2xx, and the mapping is deleted only after the Python ack.
- Capacity: 1 GB combined across the queue directories. At 80% the connection manager suspends (controlled disconnect: ingestion stops, draining continues). Only below 60% does it reconnect (hysteresis).
- QR is never logged or written to disk (redaction keys plus jid hashing in the logger). `local` mode renders to the terminal. `docker` mode has no terminal, so the bridge logs `qr_pairing_required` and stops itself. Pairing happens from a local run against the same `data/whatsapp-bridge/` directory, then the container restarts.
- Docker: private compose network, bridge port 3001 NOT published (Python reaches it by service name), 30s stop grace, non-root `node` user, `/health` healthcheck, `./data/whatsapp-bridge` bind mount. Bridge env fails closed: token, webhook secret, and FastAPI URL are required at startup.
- Verification (2026-11-19): 576 Python unit tests. DB integration 44 passed/3 skipped (`RUN_DB_SMOKE=1`). node:test 135 passed (125 at phase completion, 6 first-wave and 4 second-wave review regression tests). Ruff check clean (format drift in 15 files pre-dates this phase, and the drifting set is byte-identical to HEAD). `docker compose config` and both image builds pass. `app.main` imports. Live WhatsApp pairing and delivery were NOT exercised (no phone in this environment). The second review wave re-ran the unit, Node, ruff, and compose-config gates only; DB smoke and image builds were not re-run because Python, Docker, and schema files did not change.

## 2026-11-18 (Phase 3, WhatsApp conversations, committed in b58de9b)

- Intent gate fails closed: only `order_related` at confidence ≥ threshold (default 0.85) reaches the agent. Other categories (`human_request`/`out_of_scope`/`ambiguous`), a below-threshold verdict, and every classifier error all become human handoff. The gate owns the threshold and never raises. Classifier None (`INTENT_CLASSIFIER_ENABLED=false`) is documented dev-mode allow-all, never a production posture.
- The intent classifier runs on a separate SLM via dedicated OpenAI-compatible settings (`INTENT_CLASSIFIER_*`), with no fallback to the agent provider: the cheap fast gate must not inherit agent cost, latency, or retry semantics.
- Unknown senders: a conversation row plus the stored message (unread), no reply, no read receipt, no agent run, never a fabricated customer. `conversations.customer_id` links lazily when a registered customer later sends.
- Read receipts only AFTER the agent processed the message: the webhook receives `mark_read=False`, and the bridge suppresses receipts on that flag (Baileys sends receipts only via explicit `sock.readMessages`). Reading before answering would leak automation behavior.
- Per-conversation serialization: a PostgreSQL session advisory lock on a key derived from the first 8 bytes of sha256(phone) as a signed int64, held on a dedicated autocommit connection (no open transaction while the LLM runs). The blocking wait is intentional: the redelivered webhook then processes fresh, complete history.
- Approval lifecycle: registration (`pending_delivery`) when a run persists a draft plus an outbound summary bound to that exact outbox row. Activation happens ONLY when the adapter confirms delivery (or a delivery report reconciles that row to sent). Consumption happens only AFTER a successful `confirm_order` (post-run transcript scan), so a failed confirmation does not burn the single-use approval. A stale `active` approval is safe because `confirm_order` re-checks order status and ownership.
- Outbox delivery semantics: `unknown` (the response was lost after the request left) is never auto-resent. WhatsApp has no recipient-side idempotency key, and a blind resend can duplicate the message. Only a delivery report reconciles it. `failed` (the adapter confirmed it never went out) is retryable, capped at 3 attempts. For delivery reports `failed` is terminal: a late "delivered" for a failed send is a no-op (only pending/sending/unknown reconcile).
- `AgentError` mid-run: the partial transcript is persisted, no reply, no retry, consistent with the P2.6 rule of never retrying side-effecting work.
- Lessons from live-DB integration testing (unit fakes could not catch these, so keep the `RUN_DB_SMOKE` gate green after every repository change): (a) psycopg cannot adapt Python dicts to jsonb, so wrap with `psycopg.types.json.Json` (bitten in `MessageRepository.append_message` for `tool_calls`). (b) The intent context must be the NEWEST N text turns before seq, not the oldest N: `ORDER BY seq ASC LIMIT N` returned the wrong window, and `list_by_conversation` is DESC+LIMIT, reversed in Python. (c) `OutboxRepository.claim_next` must increment `attempts` in the claim SQL itself. The fake incremented, the SQL did not, and the retry cap never tripped (an infinite retry loop).

## 2026-11-18 (Phase 3 remediation, code-review wave, committed in b58de9b)

- Supersedes the "API auth: none exists" bullet above. The auth boundary now exists: `src/app/api/security.py`, two shared secrets, `WHATSAPP_WEBHOOK_SECRET` (`X-Webhook-Secret` header, webhook routes) and `OPERATOR_API_TOKEN` (`X-Operator-Token` header, conversation + outbox routes), compared with `hmac.compare_digest`. Empty secret: production 401s everything (fail closed), development allows (a documented dev bypass). Deliberately a boundary, not an identity system: no per-operator accounts, replay protection, or rotation, and no invented roles.
- `APP_ENVIRONMENT` (default `production`, a Literal of development/production) plus the `_production_safety` model validator: production refuses `INTENT_CLASSIFIER_ENABLED=false` and refuses `WHATSAPP_BRIDGE_URL` without `WHATSAPP_BRIDGE_TOKEN`. The safe posture is the default, and the bypass must be set explicitly.
- WhatsAppAdapter HTTP status split: 4xx → `failed` (retryable: the bridge refused the request itself), 5xx → `unknown` (never auto-resent: the request may have reached WhatsApp). The intent classifier rejects non-2xx before reading choices.
- Operator transitions serialize on the SAME per-phone advisory lock as inbound: `HandoffManager` methods default to `acquire_lock=True`, the processor calls them with `acquire_lock=False` (reentrancy prevention: advisory locks are session-scoped and the processor already holds it). The wiring uses `locking.operator_lock`, a bounded 10 s wait via a `pg_try_advisory_lock` loop. `LockAcquisitionTimeoutError` → API 503 "conversation busy": an operator request must not hang for the agent provider's 120 s read timeout.
- Approval atomicity, one transaction each: `persist_agent_run(conversation_id, new_messages, draft_order_ids=)` writes the transcript, the outbox row, and the `pending_delivery` approvals. `OutboxProcessor.send` records the send result and approval activation. `apply_delivery_report` does the same, returning `DeliveryReconciliation(row, activated)` instead of row-or-None.
- Identity mismatch: `ingest_inbound` returns `identity_mismatch=True` when the phone resolves to a different registered customer than the conversation link. The link is never overwritten. The processor stops and hands off (reason `identity_mismatch`), and it is re-checked in `reprocess_deferred`.
- Deferral: inbound during a `pending_delivery` approval is stored unread as status `deferred` (no agent run), reprocessed by `reprocess_deferred(conversation_id)` on delivery-report activation and dispatch reports. `unread_inbound` and `has_pending_for_conversation` were added.
- `mark_read=False` on all unsuccessful paths including `agent_error`. Read only after success.
- Stale `sending` recovery: migration 004 `20261118000100_phase3_1_outbox_claim_lease.sql` (additive: the `claimed_at` column, backfill `claimed_at = updated_at` for sending rows, the partial index `outbox_sending_claimed_idx`, applied to the live DB 2026-11-18, with identical copies in `src/app/database/migrations/` and `supabase/migrations/`). The claim SQL stamps `claimed_at`. `reconcile_stale_sending()` (`make_interval`, `OUTBOX_STALE_SENDING_SECONDS`, default 60) reconciles stale rows to `unknown` and never resends. Every dispatch sweeps stale first.
- Bounded agent replay: `load_agent_messages(conversation_id, limit)` returns the newest N transcript messages (`AGENT_TRANSCRIPT_MAX_MESSAGES`, default 200), dropping leading orphaned tool results so pairing stays valid. The full transcript is still persisted.
- Processor state recheck at the execution boundary and again before dispatch (the `handoff_before_dispatch` detail leaves the reply pending in the outbox).
- I1: the intent eval RAN 2026-11-18 (`uv run python scripts/evaluate_intent.py`, model `openai-gpt-oss-20b`, dataset 25 cases): accuracy 22/25 = 88%, below the 90% `MIN_ACCURACY` gate → exit code 1. The safety property holds: no expected-handoff case was classified `order_related` (no dangerous leak, no agent exposure). The 3 mismatches are `human_request`↔`out_of_scope` confusion (both hand off identically). One classifier error became fail-closed handoff. Accuracy tuning is future work, not a remediation defect.
- Verification: 567 unit tests passed. `RUN_DB_SMOKE=1` integration 43 passed / 3 skipped. Ruff check and format clean. `from app.main import app` OK. Secrets scan clean.

## 2026-11-17

- The provider LLM = Surpluss Intelligence (`api.surplusintelligence.ai/v1`, OpenAI-compatible chat completions, Bearer key `inf_…`). Verified from the official documentation (`llms.txt`, the API reference) and live: the `GET /v1/models` catalog lists `glm-5.3` (tools yes, 1M context), and a fake key produces the documented error envelope (401 `invalid_api_key` plus `request_id`). The API key and model come from configuration (`OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` with the canonical URL as default). The variable names were kept at the project owner's request.
- The provider adapter uses synchronous `httpx`, not the OpenAI SDK: the provider documentation states that legacy non-streaming requests always return HTTP 200 even on failure (the error is in the body) and warns against success decisions based on status. The adapter branches on the body (`error`/`choices`), with no new dependency and no automatic retry. Chat Completions was chosen, and the Responses API was not forced in.
- Agent architecture: an explicit Python orchestrator (`src/app/agents/orchestrator.py`) that speaks only the internal schema (`AgentMessage` in, `AgentResponse` out). The entire provider wire format is confined to `src/app/agents/providers/surpluss.py`. The system instructions live separately (`instructions.py`, in Indonesian: the backend is authoritative, inventing prices/stock is forbidden, claiming an operation succeeded without a successful backend result is forbidden). There is no `providers/base.py`: an interface with one implementation is an abstraction without a second consumer. A Protocol gets extracted when a second provider exists. P2.1 detects tool calls (`kind="tool_calls"`, raw JSON string arguments) but does not execute them.
- Conversation context belongs to the application: the endpoint is stateless, and each call sends the full history. `AgentInput` rejects system-role messages (the instructions are injected only by the orchestrator), and the customer identity never enters the agent input.
- The P2.2 tool layer: `src/app/tools/`, OpenAI-standard tool definitions (`definitions.py`, Indonesian descriptions, inline JSON Schema without `$ref`) plus `ToolRegistry` (`registry.py`, rejects duplicates/unknown names) plus `ToolError`/`DuplicateToolError`/`UnknownToolError`. The schemas are hand-written, not Pydantic `model_json_schema()`, because Pydantic emits `$defs`/`format: uuid` that are not verified safe across providers. The sync with the P2.3 Pydantic models is guarded by a test (`set(ARGUMENT_MODELS) == set(build_default_registry().names())`). Invariant: no definition accepts `customer_id`, prices, or approval arguments. The adapter's `complete(messages, tools=None)` sends `tools` when given, and `tool_choice` is not sent (the default is auto). The Phase 2 model = `deepseek-v4.1-flash-1017` (verified live in the catalog: tools yes, context 1,048,576). The `OPENAI_MODEL` value lives in `.env`, and the code stays model-agnostic.
- The P2.3 trust boundary: the `ToolContext` frozen dataclass (customer_id UUID coerced at the boundary, conversation_id, `approved_order_id: UUID | None` default None) separated from the strict Pydantic argument models (`SearchProductsArgs`/`CreateDraftOrderArgs`/`ConfirmOrderArgs`, `extra="forbid"`). An approval names ONE order, replacing `confirm_order_approved: bool` from the Phase 2 review revision, and only `with_confirm_order_approval(order_id)` from application logic sets it. The asymmetry is deliberate: full validation for model output (an external source), light coercion for context from trusted application code. `parse_tool_arguments` rejects broken JSON (a separate class for observability), schema violations (a (location, message) summary that is model-safe), and unknown names. The duplicate-product rule is not duplicated. It stays in the `OrderCreate` validator.
- P2.4 tool execution: `ToolExecutor.execute(call, context)` ALWAYS returns a structured `ToolResult` (stable categories `unknown_tool`/`malformed_arguments`/`invalid_arguments`/`unauthorized`/`not_found`/`inactive`/`missing_data`/`business_rule`/`execution_error`, Indonesian messages, details carry identifiers only). Unexpected failures are sanitized (the exception class name only). Handlers are pure translators: validated arguments plus context become a service request, and Decimal values become strings at the boundary. Handlers contain no SQL, repositories, or transactions. Confirmation has two gates: explicit single-order approval (`context.approved_order_id` must equal `args.order_id`, and the handler rejects any other order BEFORE any service call) and then draft ownership via `OrderService.get_order` (an additive read workflow, TOCTOU-safe because the order's `customer_id` is immutable and the status transition stays guarded by `confirm_order` itself). `map_service_error` maps 14 service exceptions to categories (exhaustiveness guarded by a test: every `ServiceError` subclass must be listed, `OrderTotalUpdateError` → `execution_error`, no silent generic fallback). `missing_data` (price/inventory/limit not yet present) is distinct from `not_found` (a missing entity). The decision not to add an authorization parameter to `confirm_order`: agent rules must not descend into the business layer.
- P2.5 multi-round orchestration: `AgentMessage` = the full transcript protocol (assistant `content` XOR `tool_calls`, `tool` messages require `tool_call_id` plus JSON content, per-role validation). `AgentOrchestrator.run(input, context)` loops provider→ToolExecutor→provider until the final text. `AgentRoundLimitError` is an exception, not a fabricated answer (default `DEFAULT_MAX_TOOL_ROUNDS = 5`). `AgentRunResult(final_text, response_id, transcript)` carries the transcript WITHOUT system instructions, ending on the final assistant text turn (a replay shows the model its own last answer), persisted by the caller and replayed as history in `AgentInput`. The last message must be from the user, and constructing `AgentInput` requires each tool-call assistant turn to be completed by exactly one tool result per call id (orphan/stray/duplicate results are rejected). Tool results are sent as full `ToolResult` JSON. Failures become data the model reads. Each `tool_call_id` gets exactly one result (no holes in the transcript). The `ToolExecutor.execute(tool_call_id, tool_name, arguments, context)` signature refactor to primitives: the `app.tools` package no longer imports `app.agents` (direction: orchestrator → tools → services). Transcript wire serialization is concentrated in the provider's `_wire_message`.
- P2.6 execution control: the tool-call limit is checked BEFORE execution. A batch exceeding `max_tool_calls_per_round` (8) or `max_tool_calls_total` (16) is rejected whole via `AgentToolCallLimitError` (a partial batch is forbidden: the model must never see half a success). Transient-only retry lives in the PROVIDER (completion calls have no business side effects): `AgentRateLimitError` → wait `Retry-After` (≤ an 8 s cap, longer → fail now), `AgentProviderUnavailableError` → exponential backoff 0.5 s/1.0 s, max 2 retries. Timeouts are NOT retried (120 s already burned, and a retry doubles the customer's wait). Tool execution is NEVER retried (business side effects). Observability via `AgentRunEvent` in `AgentRunResult.events`: correlation_id (`ToolContext.conversation_id`), response_id, tool/call ids, ok, category, duration (an injectable clock), no raw arguments/message contents/credentials (asserted by tests). Configuration via constructor parameters. Env wiring followed with the application layer (`config.py` CRLF untouched). A failed run's events still ride the exception (classification), but the base `AgentError` now carries `partial_transcript`/`partial_events`, attached by the orchestrator when a run fails after work started (events non-empty, None before any work). The caller can persist the side effects that already happened, with no blind retry.
- P2.7 order-flow verification: integration tests on the real path (`tests/test_agent_order_flow.py`), real orchestrator, executor, handlers, and validation, a scripted provider (`ScriptedProvider` records the messages the model saw), faked services. Causal proof: the model answers "confirmed" ONLY after it receives the `ok=true` tool message, and approval/ownership rejections reach the model before it answers. Decision: zero new production code. The mechanics were already in place from P2.3–P2.6. Ambiguity is guaranteed from the data side (all candidates sent, no automatic draft). Model language compliance awaited the live smoke. Explicit-approval detection was simulated (it belongs to the Phase 3 channel layer).
- P2.8 live verification (credentials available in `.env`, model `deepseek-v4.1-flash-1017`): `RUN_AGENT_SMOKE=1` 3 passed, meaning the real model produces valid `tool_calls` (registered names, JSON-object arguments) from our standard OpenAI tool definitions, and the FULL orchestrator loop converges against the live provider (the tooled transcript is accepted back, a final text answer arrives, the observability events are filled). Confirms the P2.1 decision: raw OpenAI format with no transformation = zero interop problems. - Shared price-list resolution lives in `src/app/services/price_list_resolver.py` (`resolve_price_list` + `GENERAL_PRICE_LIST_CODE`): the assigned list when `customers.price_list_id` is set, GENERAL otherwise. `OrderService` and `ProductInquiryService` resolve identically inside their own `transaction()`. ## 2026-11-16

- Keep project memory split by purpose. `AGENTS.md` contains mandatory agent rules, `docs/PROJECT_CONTEXT.md` contains stable facts, `docs/DECISIONS.md` contains durable choices, and `docs/TASKS.md` contains active work state.
- Keep the database connection lifecycle in `src/app/database/connection.py`. Repository methods use parameterized SQL and let the caller own transactions where a workflow spans multiple writes.
- Keep database-enforced invariants in the Supabase migration. Put cross-row workflow checks, such as requiring order items before confirmation, in services when those services are implemented.
- Keep the OpenAI agent loop deferred until the core operations and order lifecycle are implemented.
- Approved Full Connection Injection: all repositories receive their connection from the caller, for read methods as well as write methods. This extends the caller-owned-transactions rule above from multi-write workflows to every database operation. `transaction()` (or a future approved connection manager) owns connection creation, boundaries, commit, and rollback. Repositories own SQL execution and cursor lifecycle only. They never import `get_connection`, never open or close connections, and never call `commit()`, `rollback()`, or `BEGIN`.
- Approved service-layer convention (first service: `OrderService`): services receive repositories via constructor injection. Each workflow runs inside one `transaction()` and passes that connection to every repository call. Commit happens only after all steps succeed, and any exception rolls back the whole workflow. Services never execute SQL, open connections, or manage transactions. Business-rule failures raise `app.services.exceptions` domain errors (each carrying the offending identifier). Psycopg errors propagate untouched for a future API layer to map.
- Order draft business rules: unit prices always resolve backend-side from the customer's price list (fallback `GENERAL` when `customers.price_list_id` is NULL), and client input never carries prices. Inactive customers cannot create new draft orders. Inactive products cannot be added to new draft orders. Inactive price lists are not rejected (no existing rule found, a documented assumption). Draft creation is deliberately side-effect free: no inventory reservation, stock change, credit-limit validation, or `outstanding_balance` change.
- Inactivity and confirmation (approved rule): an existing draft order remains eligible for confirmation even if the customer or a product later becomes inactive. `confirm_order` never checks `is_active`. Inactivity only blocks new draft creation, never the confirmation of an existing draft.
- Order confirmation design: one `transaction()` under READ COMMITTED with pessimistic `SELECT ... FOR UPDATE` locking in the migration 001 order: the customer row first (serializing concurrent credit checks for one customer), then the order row (re-read under lock, must still be draft), then the inventory rows in ascending product_id. No SERIALIZABLE isolation: the row locks plus the guarded `mark_confirmed` UPDATE (`WHERE status = 'draft'`) make duplicate confirmation impossible. Credit exposure is `outstanding_balance` + the sum of confirmed-order totals + the order total. Confirmation never modifies `outstanding_balance` or `on_hand_stock` (reserved_stock only).
- Credit-limit semantics (resolved by migration 002, applied 2026-11-16): `customers.credit_limit` is nullable with no default. NULL = not configured → `confirm_order` raises `CreditLimitNotConfiguredError` (never treated as unlimited). 0 = a configured zero limit → any positive order is rejected with `CreditLimitExceededError`. Positive = normal validation. Migration 001's `NOT NULL DEFAULT 0` collapsed NULL and 0 into one state. Migration 002 dropped NOT NULL and DEFAULT with no data rewrite (existing zeros stay zero, the CHECK constraint is untouched, NULL passes it). The earlier spec-vs-schema gap (the NULL branch unreachable live, the zero-limit integration substitute) is closed: NULL is reachable and covered by integration tests.
- `EmptyOrderError` was added beyond the spec's exception list because migration 001 requires the confirm service to reject zero-item orders (not expressible as a SQL constraint).
- `InventoryRepository` is no longer read-only by design: the services-never-run-SQL rule dominates, so the reservation SQL (`lock_by_product_ids`, `reserve_stock`) lives in the repository while stock-sufficiency decisions stay in the service.
