# Decisions

## 2026-11-18 (Phase 3, WhatsApp conversations; working tree, uncommitted)

- Intent gate fails closed: only `order_related` at confidence ≥ threshold (default 0.85) reaches the agent; other categories (`human_request`/`out_of_scope`/`ambiguous`), below-threshold, and every classifier error become human handoff. The gate owns the threshold and never raises. Classifier None (`INTENT_CLASSIFIER_ENABLED=false`) is documented dev-mode allow-all, never a production posture.
- Intent classifier runs on a separate SLM via dedicated OpenAI-compatible settings (`INTENT_CLASSIFIER_*`), with no fallback to the agent provider: the cheap fast gate must not inherit agent cost, latency, or retry semantics.
- Unknown senders: conversation row + stored message (unread), no reply, no read receipt, no agent run, never a fabricated customer. `conversations.customer_id` links lazily when a registered customer later sends.
- Read receipts only AFTER the agent processed the message (webhook receives with `mark_read=False`; the bridge suppresses receipts on that flag — Baileys sends receipts only via explicit `sock.readMessages`). Reading before answering would leak automation behavior.
- Per-conversation serialization: PostgreSQL session advisory lock on a key derived from sha256(phone) first 8 bytes as signed int64, held on a dedicated autocommit connection (no open transaction while the LLM runs); blocking wait is intentional — the redelivered webhook then processes fresh, complete history.
- Approval lifecycle: registration (`pending_delivery`) when a run persists a draft + outbound summary bound to that exact outbox row; activation ONLY when the adapter confirms delivery (or a delivery report reconciles that row to sent); consumption only AFTER a successful `confirm_order` (post-run transcript scan), so a failed confirmation does not burn the single-use approval. A stale `active` approval is safe because `confirm_order` re-checks order status and ownership.
- Outbox delivery semantics: `unknown` (response lost after the request left) is never auto-resent — WhatsApp has no recipient-side idempotency key, a blind resend can duplicate the message; only a delivery report reconciles it. `failed` (adapter confirmed it never went out) is retryable, capped attempts (3); for delivery reports `failed` is terminal — a late "delivered" for a failed send is a no-op (only pending/sending/unknown reconcile).
- API auth: none exists project-wide yet; webhook and operator routes are documented as requiring auth before production (module docstrings + `docs/notes/P3-whatsapp-adapter.md` §6).
- `AgentError` mid-run: partial transcript persisted, no reply, no retry — consistent with the P2.6 rule of never retrying side-effecting work.
- Lessons from live-DB integration testing (unit fakes could not catch these; keep the `RUN_DB_SMOKE` gate green after every repository change): (a) psycopg cannot adapt Python dicts to jsonb — wrap with `psycopg.types.json.Json` (bitten in `MessageRepository.append_message` for `tool_calls`); (b) intent context must be the NEWEST N text turns before seq, not the oldest N (`ORDER BY seq ASC LIMIT N` returned the wrong window; `list_by_conversation` is DESC+LIMIT, reversed in Python); (c) `OutboxRepository.claim_next` must increment `attempts` in the claim SQL itself — the fake incremented, the SQL did not, and the retry cap never tripped (infinite retry loop).

## 2026-11-18 (Phase 3 remediation, code-review wave; working tree, uncommitted)

- Supersedes the "API auth: none exists" bullet above. Auth boundary now exists: `src/app/api/security.py`, two shared secrets — `WHATSAPP_WEBHOOK_SECRET` (`X-Webhook-Secret` header, webhook routes) and `OPERATOR_API_TOKEN` (`X-Operator-Token` header, conversation + outbox routes) — compared with `hmac.compare_digest`. Empty secret: production 401s everything (fail closed), development allows (documented dev bypass). Deliberately a boundary, not an identity system: no per-operator accounts, replay protection, or rotation — no invented roles.
- `APP_ENVIRONMENT` (default `production`, Literal development/production) + `_production_safety` model_validator: production refuses `INTENT_CLASSIFIER_ENABLED=false` and refuses `WHATSAPP_BRIDGE_URL` without `WHATSAPP_BRIDGE_TOKEN`. Safe posture is the default; the bypass must be set explicitly.
- WhatsAppAdapter HTTP status split: 4xx → `failed` (retryable; bridge refused the request itself), 5xx → `unknown` (never auto-resent; request may have reached WhatsApp). Intent classifier rejects non-2xx before reading choices.
- Operator transitions serialize on the SAME per-phone advisory lock as inbound: `HandoffManager` methods default `acquire_lock=True`, processor calls them with `acquire_lock=False` (reentrancy prevention: advisory locks are session-scoped and the processor already holds it); wiring uses `locking.operator_lock` — bounded 10s wait via a `pg_try_advisory_lock` loop. `LockAcquisitionTimeoutError` → API 503 "conversation busy": an operator request must not hang for the agent provider's 120s read timeout.
- Approval atomicity, one transaction each: `persist_agent_run(conversation_id, new_messages, draft_order_ids=)` writes transcript + outbox row + `pending_delivery` approvals; `OutboxProcessor.send` records send result + approval activation; `apply_delivery_report` the same, returning `DeliveryReconciliation(row, activated)` instead of row-or-None.
- Identity mismatch: `ingest_inbound` returns `identity_mismatch=True` when the phone resolves to a different registered customer than the conversation link; the link is never overwritten; the processor stops and hands off (reason `identity_mismatch`); also re-checked in `reprocess_deferred`.
- Deferral: inbound during a `pending_delivery` approval is stored unread as status `deferred` (no agent run), reprocessed by `reprocess_deferred(conversation_id)` on delivery-report activation and dispatch reports; `unread_inbound` + `has_pending_for_conversation` added.
- `mark_read=False` on all unsuccessful paths including `agent_error`; read only after success.
- Stale `sending` recovery: migration 004 `20261118000100_phase3_1_outbox_claim_lease.sql` (additive: `claimed_at` column, backfill `claimed_at = updated_at` for sending rows, partial index `outbox_sending_claimed_idx`; applied to the live DB 2026-11-18; identical copies in `src/app/database/migrations/` and `supabase/migrations/`). Claim SQL stamps `claimed_at`; `reconcile_stale_sending()` (`make_interval`, `OUTBOX_STALE_SENDING_SECONDS`, default 60) reconciles stale rows to `unknown`, never resends; every dispatch sweeps stale first.
- Bounded agent replay: `load_agent_messages(conversation_id, limit)` returns the newest N transcript messages (`AGENT_TRANSCRIPT_MAX_MESSAGES`, default 200), dropping leading orphaned tool results so pairing stays valid; the full transcript is still persisted.
- Processor state recheck at the execution boundary and again before dispatch (detail `handoff_before_dispatch` leaves the reply pending in the outbox).
- I1: intent eval RAN 2026-11-18 (`uv run python scripts/evaluate_intent.py`, model `openai-gpt-oss-20b`, dataset 25 cases): accuracy 22/25 = 88%, below the 90% `MIN_ACCURACY` gate → exit code 1. Safety property holds: no expected-handoff case was classified `order_related` (no dangerous leak, no agent exposure); the 3 mismatches are `human_request`↔`out_of_scope` confusion (both hand off identically); 1 classifier error → fail-closed handoff. Accuracy tuning is future work, not a remediation defect.
- Verification: 567 unit tests passed; `RUN_DB_SMOKE=1` integration 43 passed / 3 skipped; ruff check + format clean; `from app.main import app` OK; secrets scan clean.

## 2026-11-16

- Keep project memory split by purpose. `AGENTS.md` contains mandatory agent rules, `docs/PROJECT_CONTEXT.md` contains stable facts, `docs/DECISIONS.md` contains durable choices, and `docs/TASKS.md` contains active work state.
- Keep database connection lifecycle in `src/app/database/connection.py`. Repository methods use parameterized SQL and let the caller own transactions where a workflow spans multiple writes.
- Keep database-enforced invariants in the Supabase migration. Put cross-row workflow checks, such as requiring order items before confirmation, in services when those services are implemented.
- Keep the OpenAI agent loop deferred until the core operations and order lifecycle are implemented.
- Approved Full Connection Injection: all repositories receive their connection from the caller, for read methods as well as write methods. This extends the caller-owned-transactions rule above from multi-write workflows to every database operation. `transaction()` (or a future approved connection manager) owns connection creation, boundaries, commit, and rollback. Repositories own SQL execution and cursor lifecycle only; they never import `get_connection`, never open or close connections, and never call `commit()`, `rollback()`, or `BEGIN`.
- Approved service-layer convention (first service: `OrderService`): services receive repositories via constructor injection; each workflow runs inside one `transaction()` and passes that connection to every repository call; commit happens only after all steps succeed, any exception rolls back the whole workflow. Services never execute SQL, open connections, or manage transactions. Business-rule failures raise `app.services.exceptions` domain errors (each carrying the offending identifier); psycopg errors propagate untouched for a future API layer to map.
- Order draft business rules: unit prices always resolve backend-side from the customer's price list (fallback `GENERAL` when `customers.price_list_id` is NULL); client input never carries prices. Inactive customers cannot create new draft orders; inactive products cannot be added to new draft orders; inactive price lists are not rejected (no existing rule found, documented assumption). Draft creation is deliberately side-effect free: no inventory reservation, stock change, credit-limit validation, or `outstanding_balance` change.
- Inactivity and confirmation (approved rule): an existing draft order remains eligible for confirmation even if the customer or a product later becomes inactive. `confirm_order` never checks `is_active`, inactivity only blocks new draft creation, never the confirmation of an existing draft.
- Order confirmation design: one `transaction()` under READ COMMITTED with pessimistic `SELECT ... FOR UPDATE` locking in the migration 001 order, customer row first (serializes concurrent credit checks for one customer), then the order row (re-read under lock, must still be draft), then inventory rows in ascending product_id. No SERIALIZABLE isolation: the row locks plus the guarded `mark_confirmed` UPDATE (`WHERE status = 'draft'`) make duplicate confirmation impossible. Credit exposure is `outstanding_balance` + sum of confirmed-order totals + the order total; confirmation never modifies `outstanding_balance` or `on_hand_stock` (reserved_stock only).
- Credit-limit semantics (resolved by migration 002, applied 2026-11-16): `customers.credit_limit` is nullable with no default. NULL = not configured → `confirm_order` raises `CreditLimitNotConfiguredError` (never treated as unlimited); 0 = configured zero limit → any positive order rejected with `CreditLimitExceededError`; positive = normal validation. Migration 001's `NOT NULL DEFAULT 0` collapsed NULL and 0 into one state; migration 002 dropped NOT NULL and DEFAULT with no data rewrite (existing zeros stay zero, CHECK constraint untouched, NULL passes it). The earlier spec-vs-schema gap (NULL branch unreachable live, zero-limit integration substitute) is closed: NULL is reachable and covered by integration tests.
- `EmptyOrderError` was added beyond the spec's exception list because migration 001 requires the confirm service to reject zero-item orders (not expressible as a SQL constraint).
- `InventoryRepository` is no longer read-only by design: the services-never-run-SQL rule dominates, so the reservation SQL (`lock_by_product_ids`, `reserve_stock`) lives in the repository while stock-sufficiency decisions stay in the service.
