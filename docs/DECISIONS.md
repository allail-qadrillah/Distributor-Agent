# Decisions

## 2026-11-17

- Provider LLM = Surpluss Intelligence (`api.surplusintelligence.ai/v1`, chat completions OpenAI-compatible, Bearer key `inf_…`). Terverifikasi dari dokumentasi resmi (`llms.txt`, API reference) dan live: katalog `GET /v1/models` memuat `glm-5.3` (tools ya, konteks 1M); kunci palsu menghasilkan envelope error terdokumentasi (401 `invalid_api_key` + `request_id`). Kunci API dan model via konfigurasi (`OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` dengan default URL kanonik); nama variabel dipertahankan sesuai permintaan pemilik proyek.
- Adapter provider memakai `httpx` sinkron, bukan OpenAI SDK: dokumentasi provider menyatakan permintaan non-streaming yang lama selalu HTTP 200 walau gagal (error di body) dan memperingatkan keputusan sukses berbasis status; adapter bercabang pada body (`error`/`choices`), tanpa dependensi baru, tanpa retry otomatis. Chat Completions dipilih, Responses API tidak dipaksakan.
- Arsitektur agen: orkestrator Python eksplisit (`src/app/agents/orchestrator.py`) hanya berbicara dalam skema internal (`AgentMessage` masuk, `AgentResponse` keluar); seluruh format kabel provider terkurung di `src/app/agents/providers/surpluss.py`; instruksi sistem terpisah (`instructions.py`, Bahasa Indonesia, backend otoritatif, dilarang mengarang harga/stok, dilarang mengklaim operasi berhasil tanpa hasil backend sukses). Tidak ada `providers/base.py`: antarmuka satu implementasi = abstraksi tanpa pemakai kedua; Protocol diekstrak saat provider kedua ada. P2.1 mendeteksi tool call (`kind="tool_calls"`, argumen string JSON mentah) tetapi tidak mengeksekusinya.
- Konteks percakapan milik aplikasi: endpoint stateless, tiap panggilan mengirim riwayat penuh; `AgentInput` menolak pesan berperan system (instruksi hanya disuntik orkestrator) dan identitas pelanggan tidak pernah masuk input agen.
- Tool layer P2.2: `src/app/tools/`, definisi tool format OpenAI standar (`definitions.py`, deskripsi Bahasa, JSON Schema inline tanpa `$ref`) + `ToolRegistry` (`registry.py`, tolak duplikat/nama tak dikenal) + `ToolError`/`DuplicateToolError`/`UnknownToolError`. Skema ditulis tangan, bukan `model_json_schema()` Pydantic, karena Pydantic memancarkan `$defs`/`format: uuid` yang tidak terverifikasi aman lintas provider; sinkronisasi dengan model Pydantic P2.3 dijaga test. Invariant: tidak ada definisi yang menerima `customer_id`, harga, atau argumen persetujuan. Adapter `complete(messages, tools=None)` mengirim `tools` bila diberikan; `tool_choice` tidak dikirim (default auto). Model terpilih fase 2 = `deepseek-v4.1-flash-1017` (terverifikasi live di katalog: tools ya, konteks 1.048.576), nilai `OPENAI_MODEL` di `.env`, kode tetap agnostik model.
- P2.3 batas kepercayaan: `ToolContext` frozen dataclass (customer_id UUID dikoersi di batas, conversation_id, `confirm_order_approved` default False, hanya `with_confirm_order_approval()` dari logika aplikasi) terpisah dari model argumen Pydantic strict (`SearchProductsArgs`/`CreateDraftOrderArgs`/`ConfirmOrderArgs`, `extra="forbid"`). Asimetri disengaja: validasi penuh untuk keluaran model (sumber eksternal), koersi ringan untuk konteks dari kode aplikasi tepercaya. `parse_tool_arguments` menolak JSON rusak (kelas terpisah untuk observabilitas), pelanggaran skema (ringkasan (lokasi, pesan) aman-untuk-model), dan nama tak dikenal. Aturan duplikat produk tidak diduplikasi, tetap satu di validator `OrderCreate`.
- P2.4 eksekusi tool: `ToolExecutor.execute(call, context)` SELALU mengembalikan `ToolResult` terstruktur (kategori stabil `unknown_tool`/`malformed_arguments`/`invalid_arguments`/`unauthorized`/`not_found`/`inactive`/`missing_data`/`business_rule`/`execution_error`; pesan Bahasa; detail hanya pengidentifikasi), kegagalan tak terduga disanitasi (nama kelas exception saja). Handler = penerjemah murni (args tervalidasi + konteks → permintaan service; Decimal → string di batas; tanpa SQL/repo/transaksi). Konfirmasi dua gerbang: `confirm_order_approved` (hanya logika aplikasi) lalu kepemilikan draft via `OrderService.get_order` (read workflow aditif; TOCTOU aman karena `customer_id` pesanan immutable, transisi status tetap dijaga `confirm_order` sendiri). `map_service_error` memetakan 13 eksepsi service ke kategori; `missing_data` (harga/inventory/limit belum ada) dibedakan dari `not_found` (entitas hilang). Keputusan tidak menambah parameter otorisasi ke `confirm_order`: aturan agen tidak turun ke lapisan bisnis.
- P2.5 orkestrasi multi-putaran: `AgentMessage` = protokol transkrip penuh (assistant `content` XOR `tool_calls`; pesan `tool` wajib `tool_call_id` + konten JSON; validasi per peran), `AgentOrchestrator.run(input, context)` loop provider→ToolExecutor→provider sampai teks akhir; `AgentRoundLimitError` (exception, bukan jawaban karangan; default `DEFAULT_MAX_TOOL_ROUNDS = 5`); `AgentRunResult(final_text, response_id, transcript)`, transkrip TANPA instruksi sistem, dipersist pemanggil dan direplay sebagai riwayat `AgentInput` (pesan terakhir wajib user). Hasil tool dikirim sebagai JSON `ToolResult` utuh, kegagalan jadi data yang dibaca model, tiap `tool_call_id` tepat satu hasil (transkrip tidak bolong). Refactor signature `ToolExecutor.execute(tool_call_id, tool_name, arguments, context)` ke primitif: paket `app.tools` tidak lagi mengimpor `app.agents` (arah: orchestrator → tools → services). Serialisasi wire transkrip terkonsentrasi di `_wire_message` provider.
- P2.6 kendali eksekusi: limit panggilan tool dicek SEBELUM eksekusi, batch melebihi `max_tool_calls_per_round` (8) atau `max_tool_calls_total` (16) ditolak utuh via `AgentToolCallLimitError` (batch parsial dilarang: model tak boleh lihat sukses setengah). Retry transien-saja DI PROVIDER (panggilan completion tanpa efek samping bisnis): `AgentRateLimitError` → tunggu `Retry-After` (≤ cap 8s; lebih → gagal sekarang), `AgentProviderUnavailableError` → backoff eksponensial 0,5s/1,0s, maks 2 retry; timeout TIDAK di-retry (120s sudah terbakar, retry menggandakan tunggu pelanggan); eksekusi tool TIDAK PERNAH di-retry (efek samping bisnis). Observabilitas `AgentRunEvent` di `AgentRunResult.events`: correlation_id (`ToolContext.conversation_id`), response_id, tool/call id, ok, kategori, durasi (clock injectable), tanpa argumen mentah/isi pesan/kredensial (ditegaskan test). Konfigurasi via parameter konstruktor; env wiring menyusul bersama lapisan aplikasi (`config.py` CRLF tak tersentuh). Event run yang gagal tidak dikembalikan, klasifikasi dibawa exception.
- P2.7 verifikasi alur pesanan: test integrasi jalur nyata (`tests/test_agent_order_flow.py`), orkestrator + executor + handler + validasi asli, provider di-script (`ScriptedProvider` merekam pesan yang dilihat model), service di-fake. Bukti kausal: model menjawab "terkonfirmasi" HANYA setelah pesan tool `ok=true` diterimanya; penolakan approval/ownership terlihat model sebelum dijawab. Keputusan: nol kode produksi baru, mekanisme sudah mekanis dari P2.3–P2.6; ambiguitas dijamin dari sisi data (semua kandidat terkirim + tidak ada draft otomatis), kepatuhan bahasa model menunggu smoke hidup; deteksi persetujuan eksplisit disimulasikan (milik lapisan kanal fase berikutnya).
- P2.8 verifikasi live (kredensial tersedia di `.env`, model `deepseek-v4.1-flash-1017`): `RUN_AGENT_SMOKE=1` 3 passed, model nyata mengeluarkan `tool_calls` valid (nama terdaftar, argumen JSON objek) dari definisi tool standar kita, dan loop orkestrator PENUH konvergen terhadap provider hidup (transkrip ber-tool diterima balik, jawaban teks akhir, event observabilitas terisi). Konfirmasi keputusan P2.1: format OpenAI mentah tanpa transformasi = nol masalah interop. Sisa terbuka fase 3: agen → DB dalam satu percakapan hidup, evaluasi kepatuhan isi jawaban, wiring env limit/retry di lapisan aplikasi.
- Shared price-list resolution lives in `src/app/services/price_list_resolver.py` (`resolve_price_list` + `GENERAL_PRICE_LIST_CODE`): assigned list when `customers.price_list_id` is set, GENERAL otherwise. `OrderService` and `ProductInquiryService` resolve identically inside their own `transaction()`. The resolver does SQL-free orchestration only, it takes the caller's connection and `PriceRepository`; product-price fallback (GENERAL when a product misses the customer's list) is deliberately absent and stays a per-service `ProductPriceNotFoundError`.
- Product search policy (Product Inquiry): exact case-insensitive SKU match (`ProductRepository.search_by_exact_sku`, active products only) takes priority and short-circuits the broader `search_by_name_or_alias` partial search; all matching candidates are returned, never an arbitrary first pick. `get_by_sku` stays case-sensitive exact single-row lookup for other callers.
- Product Inquiry is read-only: one `transaction()` gives a consistent snapshot (customer, price list, prices, inventory) but writes nothing; no stock reservation. Missing data is an error, not a default, missing price raises `ProductPriceNotFoundError`, missing inventory row raises `InventoryNotFoundError` (never zero stock); an existing zero `available_stock` is a legitimate answer.

## 2026-11-16

- Keep project memory split by purpose. `AGENTS.md` contains mandatory agent rules, `docs/PROJECT_CONTEXT.md` contains stable facts, `docs/DECISIONS.md` contains durable choices, and `docs/TASKS.md` contains active work state.
- Keep database connection lifecycle in `src/app/database/connection.py`. Repository methods use parameterized SQL and let the caller own transactions where a workflow spans multiple writes.
- Keep database-enforced invariants in the Supabase migration. Put cross-row workflow checks, such as requiring order items before confirmation, in services when those services are implemented.
- Keep the OpenAI agent loop deferred until the core operations and order lifecycle are implemented.
- Approved Full Connection Injection: all repositories receive their connection from the caller, for read methods as well as write methods. This extends the caller-owned-transactions rule above from multi-write workflows to every database operation. `transaction()` (or a future approved connection manager) owns connection creation, boundaries, commit, and rollback. Repositories own SQL execution and cursor lifecycle only; they never import `get_connection`, never open or close connections, and never call `commit()`, `rollback()`, or `BEGIN`.
- Approved service-layer convention (first service: `OrderService`): services receive repositories via constructor injection; each workflow runs inside one `transaction()` and passes that connection to every repository call; commit happens only after all steps succeed, any exception rolls back the whole workflow. Services never execute SQL, open connections, or manage transactions. Business-rule failures raise `app.services.exceptions` domain errors (each carrying the offending identifier); psycopg errors propagate untouched for a future API layer to map.
- Order draft business rules: unit prices always resolve backend-side from the customer's price list (fallback `GENERAL` when `customers.price_list_id` is NULL); client input never carries prices. Inactive customers cannot create new draft orders; inactive products cannot be added to new draft orders; inactive price lists are not rejected (no existing rule found, documented assumption). Draft creation is deliberately side-effect free: no inventory reservation, stock change, credit-limit validation, or `outstanding_balance` change.
- Inactivity and confirmation (approved rule): an existing draft order remains eligible for confirmation even if the customer or a product later becomes inactive. `confirm_order` never checks `is_active`, inactivity only blocks new draft creation, never the confirmation of an existing draft.
- Order confirmation design: one `transaction()` under READ COMMITTED with pessimistic `SELECT ... FOR UPDATE` locking in the migration 001 order, customer row first (serializes concurrent credit checks for one customer), then the order row (re-read under lock, must still be draft), then inventory rows in ascending product_id. No SERIALIZABLE isolation: the row locks plus the guarded `mark_confirmed` UPDATE (`WHERE status = 'draft'`) make duplicate confirmation impossible. Credit exposure is `outstanding_balance` + sum of confirmed-order totals + the order total; confirmation never modifies `outstanding_balance` or `on_hand_stock` (reserved_stock only).
- Credit-limit semantics (resolved by migration 002, applied 2026-11-16): `customers.credit_limit` is nullable with no default. NULL = not configured → `confirm_order` raises `CreditLimitNotConfiguredError` (never treated as unlimited); 0 = configured zero limit → any positive order rejected with `CreditLimitExceededError`; positive = normal validation. Migration 001's `NOT NULL DEFAULT 0` collapsed NULL and 0 into one state; migration 002 dropped NOT NULL and DEFAULT with no data rewrite (existing zeros stay zero, CHECK constraint untouched, NULL passes it). The earlier spec-vs-schema gap (NULL branch unreachable live, zero-limit integration substitute) is closed: NULL is reachable and covered by integration tests.
- `EmptyOrderError` was added beyond the spec's exception list because migration 001 requires the confirm service to reject zero-item orders (not expressible as a SQL constraint).
- `InventoryRepository` is no longer read-only by design: the services-never-run-SQL rule dominates, so the reservation SQL (`lock_by_product_ids`, `reserve_stock`) lives in the repository while stock-sufficiency decisions stay in the service.
