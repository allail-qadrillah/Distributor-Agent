# Catatan Engineering, P2.4: Tool Execution & Service Integration

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi unit + regresi integrasi DB)

## 1. Tujuan

Menghubungkan tool handler ke layanan bisnis yang sudah ada: alur `panggilan tool model → registry → validasi argumen → handler → layanan bisnis → hasil tool terstruktur`. Ketiga tool (`search_products`, `create_draft_order`, `confirm_order`) kini dapat dieksekusi lewat `ToolExecutor`, dengan identitas pelanggan dari konteks terpercaya, harga dari backend, dan konfirmasi terkunci persetujuan eksplisit + kepemilikan draft.

## 2. Masalah yang diselesaikan

P2.3 memvalidasi argumen tapi hasil validasi belum punya tujuan: tidak ada pemanggil service, tidak ada hasil terstruktur yang bisa dibaca model. Tanpa executor terpusat, setiap pemanggil harus mengulang urutan registry→parse→handler→pemetaan error, tempat kegagalan bisa lolos sebagai exception mentah ke lapisan percakapan, dan model tidak pernah melihat operasi gagal (risiko: klaim sukses palsu, atau loop tanpa arah).

## 3. Konsep teknis

- **Handler = penerjemah murni.** Argumen tervalidasi + konteks terpercaya → permintaan service internal (`ProductInquiryRequest` atau `OrderCreate`). Respons service → payload dict aman-untuk-model (JSON murni, `Decimal` jadi string eksak). Tanpa SQL, tanpa repository, tanpa transaksi, tanpa aturan bisnis baru.
- **Executor = satu titik masuk.** `ToolExecutor.execute(call, context)` menjalankan seluruh alur dan MENGEMBALIKAN `ToolResult` SELALU, tidak ada exception lewat batas ini. Kegagalan apa pun jadi data yang bisa dibaca model: kategori stabil + pesan Bahasa + detail pengidentifikasi.
- **Kategori error = klasifikasi observabilitas P2.6.** `unknown_tool`, `malformed_arguments`, `invalid_arguments`, `unauthorized`, `not_found`, `inactive`, `missing_data`, `business_rule`, `execution_error`. Satu kode per kelas kegagalan, string stabil untuk pengelompokan log.
- **Konfirmasi terkunci dua gerbang.** (1) `context.confirm_order_approved`, hanya dari logika aplikasi; (2) kepemilikan draft, `get_order` lalu bandingkan `customer_id`. `customer_id` pada baris pesanan tidak bisa berubah, jadi urutan baca-lalu-konfirmasi tidak bisa diubah jadi mengonfirmasi pesanan pelanggan lain. Perlombaan status tetap mustahil karena transisi terjaga di dalam `confirm_order` sendiri.
- **Transaksi tetap milik service.** Arsitektur injeksi koneksi tak tersentuh: connection manager mengelola koneksi, service memiliki `transaction()`, repository menerima koneksi. Handler hanya memanggil metode service.

## 4. Desain arsitektur

```
AgentToolCall ──► ToolExecutor.execute(call, ToolContext)
                    │ 1. registry.has(name)?          ── tidak → unknown_tool
                    │ 2. parse_tool_arguments         ── rusak → malformed_arguments
                    │                                  ── skema → invalid_arguments (+field)
                    │ 3. registry.handler(name)       ── tanpa handler → MissingToolHandlerError (keras)
                    │ 4. handler(args, context, ToolServices)
                    │      ├─ search_products    → ProductInquiryService.search_products
                    │      ├─ create_draft_order → OrderService.create_draft_order (OrderCreate dari konteks)
                    │      └─ confirm_order      → [approval? ownership?] → get_order → confirm_order
                    │ 5. kegagalan: ToolHandlerError (otorisasi) / ServiceError (map_service_error) / Exception (sanitasi)
                    ▼
                ToolResult(ok, data | error{code, message, detail})
```

## 6. Alur eksekusi

Contoh `confirm_order` dengan persetujuan:
1. Model memanggil `confirm_order` `{"order_id": "…"}`. `AgentToolCall(id="call_9", ...)`.
2. Executor: nama ada di registry → parse → `ConfirmOrderArgs` valid.
3. Handler: `context.confirm_order_approved` True (logika aplikasi sudah memanggil `with_confirm_order_approval()`).
4. `OrderService.get_order(order_id)` → draft. `draft.customer_id == context.customer_id` → lanjut.
5. `OrderService.confirm_order(order_id)` → satu transaksi: kunci customer, kunci order, validasi kredit + stok, reservasi atomik, transisi terjaga.
6. Executor membungkus `OrderDetailResponse` → `ToolResult(ok=True, data={order_id, order_number, status: "confirmed", total_amount: "1500.00", items[...], confirmed_at})`.
7. Tanpa persetujuan → langkah 3 gagal SEBELUM service dipanggil → `ToolResult(ok=False, error={code: "unauthorized", message: "…persetujuan eksplisit…"})`.

## 8. Keputusan teknis dan alasannya

1. **Handler mengembalikan data mentah (dict), executor membungkus ToolResult.** Handler tidak tahu `tool_call_id`. Memaksa menyuntikkannya berarti parameter tanpa makna di lapisan handler. Executor pemilik identitas panggilan, pembungkusan di sana menjaga asosiasi `tool_call_id ↔ hasil` tunggal dan teruji.
2. **`OrderService.get_order` aditif, bukan ubah `confirm_order` signature.** Menambah parameter `expected_customer_id` ke `confirm_order` memindahkan aturan otorisasi agen KE service, lapisan bisnis jadi tahu urusan agen. Read workflow kecil + pengecekan di handler menjaga otorisasi di lapisan agen. TOCTOU aman karena `customer_id` pesanan tidak berubah (lihat §3).
3. **Kegagalan tak terduga disanitasi, bukan dibocorkan.** `except Exception` di executor mengembalikan `execution_error` + `{"exception_type": ...}`, nama kelas saja. Pesan (`psycopg ...: secret stuff`) tidak pernah sampai model. Test menegaskan hal ini.
4. **`MissingToolHandlerError` dibiarkan menyebar keras** (di luar blok try executor): definisi tanpa handler = kesalahan pemrograman. Menjadikannya hasil tool senyap akan menyembunyikan bug wiring. Kebalikan `unknown_tool` (kesalahan model) yang memang jadi hasil terstruktur.
5. **Perbedaan kategori `missing_data` dan `not_found`.** Entitas hilang (pelanggan, produk, atau pesanan) = `not_found`. Data PENDUKUNG hilang (harga di daftar, baris inventory, konfigurasi limit kredit) = `missing_data`. Keduanya kelas masalah berbeda: yang kedua menunjukkan dataset belum lengkap, bukan permintaan salah. `CreditLimitNotConfigured` = `missing_data` (bukan `business_rule`) karena penolakannya konfigurasi, bukan pelanggaran batas.
6. **Decimal → string di lapisan tool, bukan di service.** Service bicara `Decimal` (presisi uang). Model bicara JSON. Konversi tepat di batas penerjemahan, `str(Decimal("150.00"))` = `"150.00"` tanpa float di jalur mana pun.
7. **Tanpa test integrasi DB khusus `get_order`.** Metode = pembungkus tipis `OrderRepository.get_by_id` (teruji integrasi sendiri) + `OrderNotFoundError` (teruji unit). Regresi integrasi penuh tetap dijalankan untuk memastikan `order.py` tak regres.

## 10. Risiko dan keterbatasan

- Handler belum dipanggil dari alur percakapan nyata, orkestrator loop P2.5 menghubungkan.
- `ToolResult.error.detail` berisi pengidentifikasi (UUID, kuantitas, limit), aman untuk model. Jangan ditambah data sensitif saat detail diperluas.
- Dua transaksi terpisah di alur konfirmasi (get_order, lalu confirm_order). Benar untuk ownership (customer_id immutable), tapi draft bisa berubah status antara keduanya oleh kanal lain. `confirm_order` sendiri menolak dengan `InvalidOrderStatusError`, terpetakan `business_rule`. Aman, hanya perlu diketahui.
- Eksekusi sinkron per panggilan. Model meminta dua tool dalam satu respons = dua eksekusi berurutan (P2.5).

## 11. Pemahaman engineering

Pembelajaran inti: **kegagalan juga data**. Perhatikan perbedaan dua kegagalan konfirmasi:

```python
# (a) tanpa persetujuan, ditolak SEBELUM service dipanggil
executor.execute(_call("confirm_order", '{"order_id": "..."}'), context)
# → ToolResult(ok=False, error={code: "unauthorized",
#     message: "Konfirmasi pesanan membutuhkan persetujuan eksplisit ..."})
#    orders.get_order_ids == []  ← tidak ada sentuhan database sama sekali

# (b) stok kurang, service menolak di dalam transaksinya
executor.execute(_call("confirm_order", '{"order_id": "..."}'), approved_context)
# → ToolResult(ok=False, error={code: "business_rule",
#     message: "Konfirmasi ditolak: stok tidak mencukupi.",
#     detail: {"product_id": "...", "requested": 10, "available": 5}})
```

Keduanya `ok=False`, model TIDAK BISA melihatnya sebagai sukses, dan pesannya bisa diteruskan ke pelanggan tanpa karangan. Instruksi agen P2.1 ("jangan klaim berhasil tanpa hasil backend") kini punya penyangga mekanis: satu-satunya jalur sukses adalah `ToolResult.ok=True`, dan itu hanya terjadi kalau service benar-benar mengembalikan respons.

## 12. Langkah berikutnya (P2.5, Tool Result & Multi-Turn Orchestration)

- Perluas skema pesan: peran `tool` + `tool_call_id`, pesan assistant membawa `tool_calls` untuk dikirim balik.
- Loop orkestrator: panggil model dengan `tools` → bila `tool_calls`: eksekusi tiap panggilan via `ToolExecutor` → susun pesan `tool` (JSON `ToolResult`) → kirim riwayat yang diperbarui → ulang sampai teks akhir / batas iterasi.
- Verifikasi asosiasi `tool_call_id` ↔ hasil. Dukung beberapa panggilan per respons.
