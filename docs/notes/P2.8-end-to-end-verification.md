# Catatan Engineering, P2.8: End-to-End & Phase Review

Tanggal: 2026-11-17 · Status: selesai, fase 2 tuntas terverifikasi (unit + integrasi DB + smoke live provider dan model)

## 1. Tujuan

Menutup fase 2: matriks skenario penuh, regresi lengkap semua lapisan (unit, integrasi DB, smoke live provider), audit konsistensi dokumen, dan laporan akhir fase. Ditambah hal yang berubah sejak rencana awal disusun: kredensial `OPENAI_API_KEY` dan `OPENAI_MODEL` kini tersedia di `.env`, dan smoke live diperluas dari sekadar respons teks (P2.1) menjadi panggilan tool nyata + loop orkestrator penuh terhadap provider hidup.

## 2. Masalah yang diselesaikan

Sejak P2.2, tiap catatan mencatat risiko yang sama: "panggilan tool live belum pernah diterima dari model nyata", format respons terdokumentasi dan adapter teruji unit, tapi kecenderungan model nyata (apakah benar memilih `search_products`, apakah transkrip multi-turn kita diterima) belum dibuktikan. P2.8 menutupnya dengan dua test live baru tergerbang `RUN_AGENT_SMOKE=1`, ditambah regresi penuh sebagai gerbang rilis fase.

## 3. Konsep teknis

- **Tiga lapisan verifikasi terpisah.** (1) Unit (331): semua lapisan dengan fake, cepat, deterministik, tiap cabang kegagalan. (2) Integrasi DB (`RUN_DB_SMOKE=1`, 30 passed, 3 skipped): service + repository + PostgreSQL nyata. (3) Smoke live (`RUN_AGENT_SMOKE=1`, 3 passed): provider + model nyata tanpa DB. Gabungan (2)+(3) menutup hampir semua sela. Yang tersisa (agen → DB dalam satu percakapan hidup) menunggu lapisan aplikasi fase berikutnya.
- **Smoke live = jalur produksi, batas tetap di-fake.** Test loop live memakai `AgentOrchestrator` + `SurplussProvider` asli dengan `CannedToolExecutor` (hasil tool plausibel, tanpa database), persis arsitektur produksi minus DB. Test membuktikan model nyata menerima format wire tool kita, mengeluarkan `tool_calls` valid, menerima balik transkrip tool-result kita, dan loop konvergen ke jawaban teks.
- **Asersi hidup longgar di tempat yang benar.** Test tidak mengunci KATA-KATA model (non-deterministik), tapi mengunci BENTUKnya: `kind`, nama tool terdaftar, argumen objek JSON valid, transkrip memuat pertukaran tool, `final_text` non-kosong, event observabilitas terisi. Kepatuhan isi (Bahasa, kejujuran angka) diarahkan instruksi + deskripsi tool, diukur terpisah di masa depan bila dibutuhkan.

## 6. Alur eksekusi

Test loop live, langkah demi langkah:
1. `AgentOrchestrator(provider_hidup, CannedToolExecutor())` + `AgentInput(user: "Berapa harga Aqua 600 ml?")`.
2. Putaran 1: provider mengirim [system instruksi, user] + 3 definisi tool → model nyata menjawab `tool_calls` (`search_products`, `{"search_term": "Aqua"...}`, argumen valid JSON objek).
3. Orkestrator mengeksekusi via `CannedToolExecutor` → `ToolResult` sukses dengan produk plausibel → pesan `tool` dikirim balik (`_wire_message` → format transkrip provider).
4. Putaran 2: provider hidup MENERIMA transkrip ber-tool kita → model menjawab teks akhir (harga dari hasil tool, bukan karangan).
5. Asersi: `final_text` non-kosong, `executor.executed` non-kosong, `transcript` memuat peran `tool` dan tanpa `system`, `events` terisi.

## 8. Keputusan teknis dan alasannya

1. **Perluasan smoke live, bukan hanya menjalankan yang lama.** Smoke teks P2.1 tidak menyentuh tool sama sekali. Risiko terbuka terbesar fase justru di sana. Dua test baru (tool_calls + loop penuh) menutupnya dengan biaya minimal. Infrastruktur gerbang (`RUN_AGENT_SMOKE`, fixture skip) sudah ada.
2. **Executor di-fake pada live loop, bukan service.** Meng-fake service berarti jalur provider→transkrip→model-lagi teruji, tanpa ketergantungan data DB seeded. Menguji jalur DB nyata sudah tugas `RUN_DB_SMOKE` (lapisan service). Menggabungkan keduanya menambah ketergantungan setup tanpa menutup risiko baru.
3. **Asersi bentuk, bukan isi jawaban model.** Model non-deterministik, mengunci frasa jawaban = test flaky. Bentuk (kind, nama tool, JSON valid, konvergensi) adalah kontrak yang kode kita andalkan. Itu yang di-lock.
4. **`.env` milik pemilik, tidak pernah dibaca ke log atau di-assert.** Test hanya memeriksa `settings.openai_api_key` non-kosong dan kebersihan kebocoran (P2.1). Nilai kredensial tidak pernah muncul di output.
5. **Tanpa commit.** Semua perubahan fase 2 (P2.1–P2.8) dibiarkan tak ter-commit sesuai instruksi. Usulan pesan commit disertakan di laporan akhir untuk diputuskan pemilik.

## 10. Risiko dan keterbatasan

- **Agen → DB dalam satu percakapan hidup belum diuji** (butuh lapisan aplikasi + data seeded). Risiko rendah karena tiap sisi tervalidasi terpisah, tapi dicatat jujur di laporan akhir.
- **Kepatuhan isi jawaban model** (Bahasa, tidak mengarang angka, bertanya saat ambigu) terarah instruksi dan deskripsi tapi TIDAK diuji otomatis, hanya bentuk. Evaluasi kualitas jawaban = pekerjaan masa depan.
- **Flaky smoke live**: model kadang menjawab teks langsung tanpa tool. Test tool_calls memakai instruksi eksplisit untuk memaksa panggilan. Kalau provider berganti model default, asersi `kind` mungkin perlu dilonggarkan.
- **Biaya + latensi live smoke** (3 panggilan model), tergerbang manual, bukan CI rutin.

## 11. Pemahaman engineering

Pembelajaran fase: **verifikasi berlapis menang karena tiap lapisan punya sumber ketidakpastian yang berbeda**. Unit (331) membuktikan logika. DB smoke membuktikan SQL + transaksi + konstrain nyata. Live smoke membuktikan kontrak provider + perilaku model nyata. Yang mengejutkan di P2.8: tidak ada satu pun kegagalan pada pertemuan lapisan. Format wire tool diterima provider apa adanya (sesuai dokumentasi normalisasi), transkrip ber-tool diterima balik, model patuh memanggil tool dengan argumen JSON bersih pada percobaan pertama. Ini konsekuensi langsung keputusan P2.1: memakai format OpenAI standar mentah tanpa transformasi pintar. Semua kompleksitas interop hilang karena tidak ada yang diubah. Pelajaran praktis: **saat standar sudah ada, patuhilah secara membosankan. Setiap "perbaikan" terhadap standar adalah risiko baru**.
