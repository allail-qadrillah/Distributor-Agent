# Catatan Engineering, P2.5: Tool Result & Multi-Turn Orchestration

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi, percakapan hidup menunggu kredensial)

## 1. Tujuan

Menutup loop percakapan: hasil eksekusi tool dikirim balik ke model, model membacanya dan melanjutkan, sampai jawaban teks akhir atau batas iterasi. Skema pesan diperluas menjadi protokol transkrip penuh (peran `tool` + `tool_call_id`, giliran assistant membawa `tool_calls`), orkestrator mengeksekusi putaran tool berulang, dan hasil satu run menjadi objek yang bisa dipersist + direplay pemanggil (`AgentRunResult.transcript`).

## 2. Masalah yang diselesaikan

P2.4 menghasilkan `ToolResult` terstruktur, tapi tidak ada yang mengirimkannya ke model. Alur berhenti setelah eksekusi pertama. Tanpa protokol transkrip, tiga hal mustahil: (1) model tidak pernah melihat hasil tool sehingga tidak bisa menjawab pelanggan berdasarkan data backend; (2) riwayat percakapan dengan pertukaran tool tidak bisa dipersist, replay putaran berikutnya akan ditolak provider (pesan `tool` harus mengikuti `tool_calls`-nya); (3) model yang berulang meminta tool tanpa konvergen akan berputar selamanya tanpa batas.

## 3. Konsep teknis

- **Protokol transkrip multi-peran.** `AgentMessage` kini membentuk empat peran: `system` dan `user` (teks murni, tanpa field tool), `assistant` (teks ATAU giliran tool-call, `content` null + `tool_calls` non-kosong, XOR), `tool` (satu hasil: `tool_call_id` + konten JSON non-kosong). Aturan bentuk ditegakkan validator per peran, transkrip tidak valid gagal di lapisan agen, bukan ditolak provider secara opak.
- **Loop eksplisit dengan batas keras.** `run()` memanggil provider (dengan definisi tool) → respons teks berarti selesai. Respons `tool_calls` berarti: eksekusi tiap panggilan via `ToolExecutor`, tambahkan giliran assistant-tool-call + pesan hasil per panggilan, panggil provider lagi. `DEFAULT_MAX_TOOL_ROUNDS = 5`. Batas tercapai tanpa teks akhir → `AgentRoundLimitError` di-raise, TIDAK pernah mengarang jawaban.
- **Setiap `tool_call_id` tepat satu hasil.** Kegagalan tool menjadi data yang dibaca model (`{"ok": false, "error": {...}}`), bukan pesan yang dibuang. Transkrip yang bolong akan ditolak provider pada panggilan berikutnya.
- **Transkrip tanpa instruksi sistem.** Instruksi disuntik orkestrator setiap panggilan tapi tidak masuk `AgentRunResult.transcript`. Pemanggil mempersist transkrip bersih dan me-replay-nya sebagai riwayat `AgentInput` berikutnya. Pesan terakhir harus `user`.
- **Serialisasi wire di satu tempat.** `_wire_message` provider: giliran assistant-tool-call → `{"role": "assistant", "content": null, "tool_calls": [...]}`. Hasil tool → `{"role": "tool", "tool_call_id": ..., "content": ...}`, persis format transkrip multi-turn yang didokumentasikan provider.

## 4. Desain arsitektur

```
AgentInput(messages) ──► AgentOrchestrator.run(input, ToolContext)
                          │  putaran ≤ max_tool_rounds:
                          │    [system] + messages ──► provider.complete(..., tools)
                          │      kind=text   → AgentRunResult(final_text, response_id, transcript)
                          │      kind=tool_calls:
                          │        messages += assistant(tool_calls)
                          │        per call: ToolExecutor.execute(id, name, args, context)
                          │        messages += tool(tool_call_id, ToolResult JSON)
                          │        ulang
                          │  batas tercapai → AgentRoundLimitError (raise, bukan jawaban karangan)
                          ▼
        pemanggil mempersist AgentRunResult.transcript → AgentInput berikutnya
```

Arah lapisan: orkestrator → tools → services. Refactor yang menyertainya: `ToolExecutor.execute(tool_call_id, tool_name, arguments, context)` menerima primitif, dan paket `app.tools` tidak lagi mengimpor `app.agents` sama sekali.

## 6. Alur eksekusi

Contoh satu putaran "cek harga Aqua":
1. Pemanggil: `AgentInput(messages=[user("berapa harga Aqua?")])` + `ToolContext(customer_id=…)`.
2. Orkestrator: `provider.complete([system, user], tools=specs)` → `AgentResponse(kind="tool_calls", tool_calls=[{id: "call_1", name: "search_products", arguments: '{"search_term": "Aqua"}'}])`.
3. `messages.append(assistant(tool_calls))` lalu `executor.execute("call_1", "search_products", '{"search_term": "Aqua"}', context)` → `ToolResult(ok=True, data={products: [...]})`.
4. `messages.append(tool(tool_call_id="call_1", content=ToolResult JSON))`.
5. Putaran kedua: `provider.complete([system, user, assistant, tool], tools)` → `kind="text"` → `AgentRunResult(final_text=…, transcript=[user, assistant, tool])`.
6. Pemanggil mempersist `transcript`. Pesan pelanggan berikutnya = `[user, assistant, tool, userbaru]`.

## 8. Keputusan teknis dan alasannya

1. **`ToolExecutor.execute` diubah ke primitif (id, name, arguments, context).** Signature lama menerima `AgentToolCall` dan paket tools mengimpor paket agents, melanggar arah dependensi (orchestrator → tools → services). Primitif menjaga lapisan tool mandiri dan bisa diuji tanpa skema agen. Orkestrator membongkar `AgentToolCall` sendiri. Test lama diperbarui mengikuti.
2. **Batas putaran = exception, bukan jawaban fallback.** `AgentRoundLimitError` memaksa pemanggil memutuskan cara meminta maaf ke pelanggan. Teks karangan otomatis akan melanggar instruksi agen ("jangan klaim berhasil tanpa hasil backend") pada momen paling berbahaya, saat loop tidak sehat.
3. **`AgentRunResult.transcript` mengecualikan instruksi sistem.** Instruksi milik orkestrator dan dikirim ulang tiap panggilan (stateless). Kalau masuk transkrip persist, replay akan menyuntik instruksi dobel dan `AgentInput` (yang menolak peran system) tidak bisa dipakai untuk replay sama sekali.
4. **Hasil tool dikirim sebagai JSON `ToolResult` utuh (`model_dump_json`).** Model membaca `ok`, `data`, `error.code`, dan `error.message`, struktur yang sama dipakai P2.6 untuk observabilitas. `exclude_none=True` menjaga payload ramping (sukses tanpa blok error).
5. **XOR `content` vs `tool_calls` di giliran assistant.** Provider mendokumentasikan content null untuk giliran tool-call. Teks bersamaan tidak terdefinisi. Menolaknya di validator = transkrip selalu sendable. Test menegaskan ketiga sisi (content saja, tool_calls saja, keduanya ditolak).
6. **`max_tool_rounds` parameter konstruktor (default 5), divalidasi ≥ 1.** Konfigurasi runtime (env/`Settings`) menyusul saat lapisan aplikasi ada, sekarang nilai default konstan + batas yang bisa disuntik test.
7. **`AgentRoundLimitError` bukan turunan `AgentProviderError`.** Klasifikasi error penyedia (auth, rate limit, timeout) beda kelas dari keputusan orkestrasi. Pemanggil P2.6 akan memetakan keduanya berbeda: satu di-retry, satu dibatalkan.

## 10. Risiko dan keterbatasan

- **Batas putaran belum konfigurable via env**, konfigurasinya konstanta default + parameter konstruktor. Konfigurasi runtime menyusul bersama lapisan aplikasi (P2.6 mengatur limit secara sistematis).
- **Belum ada limit jumlah tool call per respons**, model bisa meminta banyak panggilan dalam satu giliran dan semuanya dieksekusi berurutan sinkron. P2.6 menambahkan batas per-giliran dan total per request.
- **Tanpa retry dan backoff provider**, kegagalan transien (429 + Retry-After) langsung menyebar ke pemanggil. Menyusul di P2.6.
- **Tanpa observabilitas**, belum ada logging durasi dan kategori per panggilan tool. Menyusul di P2.6.
- **Transkrip persist belum ada pemakai nyata** (lapisan WhatsApp atau API fase berikut). Replay diuji lewat test `test_history_with_prior_tool_exchange_replays`.
- **Ukuran konteks**, transkrip dipersist penuh dan dikirim ulang tiap panggilan. Untuk percakapan panjang bisa membengkak. Model terpilih konteksnya 1.048.576 token, bukan masalah pada fase ini. Trimming menyusul kalau dibutuhkan (catat di P2.6 atau P2.8 bila relevan).

## 11. Pemahaman engineering

Pembelajaran inti: **protokol transkrip adalah kontrak tipe, bukan konvensi string**. Perhatikan urutan pesan yang dikirim provider pada putaran kedua:

```python
[m.role for m in second_call_messages] == ["system", "user", "assistant", "tool"]
# assistant: content=None, tool_calls=[{id: "call_1", ...}]
# tool:      tool_call_id="call_1", content='{"tool_call_id": "call_1", "tool_name": "search_products", "ok": true, ...}'
```

Dua invariant menjaga kesehatan loop tanpa pernah memeriksa kabel secara manual: (1) `AgentMessage` validator menolak giliran assistant tanpa payload, `tool_calls` kosong, teks+tool_calls sekaligus, dan pesan `tool` tanpa id/konten, transkrip tak valid tidak mungkin terbentuk; (2) `_append_tool_round` selalu memasangkan satu hasil per `tool_call_id` (termasuk kegagalan), jadi transkrip tidak pernah bolong. Dengan dua invariant itu, satu-satunya cara loop gagal adalah kegagalan yang layak dilihat pemanggil: error provider atau batas putaran, keduanya exception eksplisit, bukan perilaku senyap.

Sisi kedua: **hasil gagal adalah konten normal, bukan kegagalan alur**. `test_failed_tool_result_is_fed_back_as_data` menegaskan loop berlanjut ke jawaban akhir setelah tool gagal, model membaca `error.code: "not_found"` lalu menjawab pelanggan dengan jujur ("produk tidak ditemukan") alih-alih percakapan mati di tengah.

## 12. Langkah berikutnya (P2.6, Error Handling & Execution Control)

- Limit eksekusi sistematis: maksimum putaran (sudah ada, dibuat konfigurable), maksimum panggilan tool per giliran, maksimum total panggilan per request, semua dengan nilai default konservatif dan penolakan terstruktur saat terlampaui.
- Kebijakan retry terbatas: hanya kegagalan transien (429 dengan Retry-After, 5xx, timeout koneksi). Tanpa auto-retry untuk operasi non-idempoten (create dan confirm) setelah eksekusi tool dimulai. Batas maksimum percobaan + jitter.
- Observabilitas tanpa kebocoran: record per panggilan (correlation id, response_id, nama tool, tool_call_id, kategori hasil, durasi, klasifikasi error) untuk log terstruktur, tanpa argumen mentah, tanpa kredensial, tanpa stack trace.
- Test: batas terlampaui, retry transien sukses atau gagal, klasifikasi error, record observabilitas berisi field tepat.
