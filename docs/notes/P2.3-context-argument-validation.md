# Catatan Engineering, P2.3: Customer Context & Argument Validation

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi)

## 1. Tujuan

Menegakkan batas kepercayaan antara data hasil model dan data milik backend: (1) konteks eksekusi terpercaya berisi identitas pelanggan, id percakapan, dan penanda persetujuan konfirmasi, semuanya dari logika aplikasi; (2) argumen mentah model (string JSON) diparse dan divalidasi ketat dengan Pydantic v2 sebelum menyentuh layanan bisnis.

## 2. Masalah yang diselesaikan

Model menghasilkan teks bebas. Output-nya bukan tipe. Tanpa validasi batas, string JSON rusak, field hilang, tipe salah, atau field hasil halusinasi (mis. `customer_id`, `unit_price`, `approved: true`) bisa mengalir sampai ke layanan bisnis. Tanpa konteks terpercaya, satu-satunya sumber identitas pelanggan adalah argumen model, yang berarti model bisa meniru pelanggan mana pun.

## 3. Konsep teknis

- **Empat konsep terpisah, tidak digabung.** (1) Argumen mentah: `AgentToolCall.arguments` string JSON apa adanya; (2) argumen tervalidasi: `SearchProductsArgs`, `CreateDraftOrderArgs`, atau `ConfirmOrderArgs`; (3) konteks terpercaya: `ToolContext`; (4) permintaan service internal (mis. `OrderCreate`), dibangun handler P2.4 dari (2)+(3). Tidak ada satu objek tak terpercaya gabungan.
- **Parse di batas, bukan di skema.** String JSON tetap mentah di `AgentToolCall` (keputusan P2.1). Parsing + validasi terjadi tepat sebelum eksekusi, titik tempat kegagalan bisa dilaporkan balik ke model sebagai hasil tool terstruktur.
- **Strict by convention.** Model argumen mewarisi `BaseSchema` proyek (`extra="forbid"`): field tak dikenal ditolak. UUID harus well-formed, kuantitas `int > 0`, `search_term` `NonBlankStr` (trim + non-kosong, cermin btrim DB).
- **Persetujuan konfirmasi bukan data model.** `ToolContext.confirm_order_approved` default `False`. Hanya `with_confirm_order_approval()` (dipanggil logika aplikasi yang membaca jawaban eksplisit pengguna) yang menyalakannya. Frozen dataclass, tak bisa dimutasi setelah dibuat.

## 4. Desain arsitektur

```
logika aplikasi (pemanggil)                      model
   │ ToolContext(customer_id, ...)                  │ AgentToolCall(name, arguments JSON mentah)
   ▼                                                ▼
   └──────────► [P2.4 handler] ◄── parse_tool_arguments(name, raw)
                     │                    │
                     │                    ├─ MalformedToolArgumentsError (bukan objek JSON)
                     │                    ├─ InvalidToolArgumentsError (skema gagal, ringkasan aman-untuk-model)
                     │                    └─ UnknownToolError (nama tak ada model argumennya)
                     ▼
        OrderCreate / ProductInquiryRequest (dibangun dari Args + Context)
```

## 6. Alur eksekusi

1. Pemanggil aplikasi membangun `ToolContext(customer_id=…, conversation_id=…)`, identitas dari kanal atau API terautentikasi.
2. Model meminta tool. `AgentToolCall.arguments` masih string JSON mentah.
3. Lapisan eksekusi (P2.4) memanggil `parse_tool_arguments(call.name, call.arguments)`.
4. `json.loads` gagal atau hasil bukan objek → `MalformedToolArgumentsError`. Validasi Pydantic gagal → `InvalidToolArgumentsError` dengan `errors=[(lokasi, pesan)]`.
5. Sukses → instans model argumen. Handler menggabungkannya dengan `ToolContext` untuk membentuk permintaan service internal.
6. Sebelum konfirmasi pesanan, handler memeriksa `context.confirm_order_approved`. Tanpa `True` (diberikan hanya oleh logika aplikasi via `with_confirm_order_approval()`), handler menolak dengan error otorisasi. Persetujuan dari argumen model tidak pernah ada jalurnya.

## 7. Ringkasan perubahan kode

Baru: `src/app/tools/context.py` (±55 baris), `src/app/tools/arguments.py` (±120), ekspor `__init__.py` diperluas, `tests/test_tool_arguments.py` + `tests/test_tool_context.py` (27 test). Tanpa perubahan service, tanpa migrasi, tanpa dependensi baru. Tiga kelas P2.2 tak tersentuh.

## 8. Keputusan teknis dan alasannya

1. **Dataclass frozen untuk konteks, Pydantic untuk argumen.** Konteks dibangun kode aplikasi tepercaya, validasi penuh di sana berarti memvalidasi diri sendiri. Cukup koersi UUID di batas (`__post_init__`). Argumen berasal dari model, sumber eksternal tak terpercaya, jadi validasi skema penuh (`extra="forbid"`). Asimetri ini disengaja: ketat ke luar, ringan ke dalam.
2. **Duplikasi aturan minimal.** `DraftOrderItemArgs` = `OrderItemCreate` bentuknya (product_id + quantity>0) tapi didefinisikan ulang di lapisan tool, bukan diimpor, karena model argumen berisi subset tanpa `customer_id` dan boleh berbeda evolusi. Aturan duplikasi produk TIDAK diduplikasi, dibiarkan satu di validator `OrderCreate` (handler P2.4 membangun `OrderCreate` nyata yang memvalidasi sekali lagi). Test sinkronisasi menjaga field wire = field Pydantic = kontrak service.
3. **Ringkasan error aman untuk model.** `InvalidToolArgumentsError.errors` hanya pasangan (lokasi, pesan pendek) dari `ValidationError.errors()`, cukup bagi model memperbaiki percobaan berikutnya, tanpa stack trace/detail internal. Pesan pydantic sudah self-contained ("Input should be a valid UUID...").
4. **`MalformedToolArgumentsError` terpisah dari `InvalidToolArgumentsError`.** JSON rusak dan skema gagal adalah kategori berbeda untuk klasifikasi observabilitas (P2.6). Yang pertama indikasi output model korup. Yang kedua normal dalam iterasi tool.
5. **`parse_tool_arguments` juga menolak nama tak dikenal** (`UnknownToolError`) meski registry sudah menjaga. Penjaga ganda di batas murah. Satu jalur lupa = identitas bocor.

## 10. Risiko dan keterbatasan

- `parse_tool_arguments` dipanggil lapisan eksekusi P2.4, sendirian belum terhubung ke alur runtime. Milestone ini komponen batas + kontrak, penghubungnya menyusul.
- `ToolContext.metadata` bebas isi string, pemanggil harus menjaga tidak menaruh data sensitif (dok: "never business data"). Belum ada penegakan runtime.
- Penentu "persetujuan eksplisit" (deteksi 'ya, konfirmasi') tinggal di tangan pemanggil aplikasi fase berikutnya. P2.7 menguji alurnya dari sisi agent.
- Kuantitas bertipe `int`, jumlah fraksional (mis. 1.5) ditolak bersih. Model float seperti `10.0` gagal validasi int. Perilaku konsisten dengan skema wire (`type: integer`).

## 11. Pemahaman engineering

Prinsip inti: **jangan pernah memvalidasi gabungan objek terpercaya + tak terpercaya**. Pemisahan tipe adalah pemisahan kepercayaan. Contoh konkret penyelundupan yang kini mustahil:

```python
# model mencoba menetapkan identitas + harga + approval sendiri:
parse_tool_arguments(
    "create_draft_order",
    '{"items": [{"product_id": "…", "quantity": 1, "unit_price": 1.0}],'
    ' "customer_id": "uuid-pelanggan-lain"}',
)
# → InvalidToolArgumentsError: unit_price (extra), customer_id (extra) ditolak;
#   harga & identitas tidak punya field yang bisa diisi.
# Approval pun mustahil dari arah ini: ConfirmOrderArgs hanya order_id,
#   dan approved=True dari ToolContext hanya lewat logika aplikasi.
```

Sisi lain: yang TIDAK divalidasi di sini adalah pelanggan benar-benar ada di DB, stok cukup, dan kredit cukup. Itu bukan validasi bentuk, itu aturan bisnis, tetap di service (P2.4). Batas lapisan = bentuk dan kepercayaan. Lapisan service = kebenaran bisnis.

## 12. Langkah berikutnya (P2.4, Tool Execution & Service Integration)

- Handler ketiga tool: `search_products` (→ `ProductInquiryService.search_products`), `create_draft_order` (→ `OrderService.create_draft_order`, customer_id dari `ToolContext`), `confirm_order` (→ `OrderService.confirm_order` setelah cek ownership draft + `context.confirm_order_approved`).
- Ownership draft perlu read workflow kecil di `OrderService` (aditif, tanpa ubah aturan) karena `confirm_order(order_id)` tidak memeriksa pemilik.
- Hasil tool terstruktur (data sukses / error terklasifikasi), pemetaan eksepsi service → kategori hasil, tanpa SQL di handler, tanpa duplikasi aturan bisnis.
