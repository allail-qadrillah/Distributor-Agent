# Catatan Engineering, P2.1: Agent Foundation

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi + jalur error live, smoke test positif menunggu kredensial)

## 1. Tujuan

Membangun fondasi AI Agent: aplikasi bisa mengirim pesan pengguna beserta instruksi agen ke model GLM (via Surpluss Intelligence), menerima balasan, membedakan balasan teks biasa dari permintaan pemanggilan tool, menormalkannya menjadi objek internal, dan menangani error provider secara aman. Milestone ini tidak mengeksekusi tool apa pun.

## 2. Masalah yang diselesaikan

Sebelum P2.1 tidak ada jalur komunikasi ke LLM sama sekali. Seluruh logika bisnis (harga, stok, pesanan) sudah ada di service layer, tetapi belum ada komponen yang bisa: (1) berbicara dengan model secara terkendali, (2) menjaga batas arsitektur `api → tools → services → repositories → database` saat LLM masuk, dan (3) memetakan kegagalan provider menjadi error aplikasi yang tidak membocorkan kredensial.

## 3. Konsep teknis

- **Orkestrator agen eksplisit (Python murni).** Alur satu putaran ditulis sebagai Python biasa: gabungkan instruksi + riwayat pesan → panggil provider → kembalikan hasil ternormalisasi. Tidak ada LangGraph atau framework lain. Alurnya pendek, semua langkah terlihat, mudah diuji.
- **Adapter provider.** Modul kecil satu-satunya yang tahu format kabel (wire format) Surpluss Intelligence. Ia menerima `AgentMessage` internal dan mengembalikan `AgentResponse` internal. Orkestrator tidak pernah melihat JSON provider.
- **Balasan teks vs tool call.** Chat Completions OpenAI-compatible: balasan teks datang di `choices[0].message.content` (string). Permintaan tool datang di `choices[0].message.tool_calls[]` (`id`, `type: "function"`, `function.name`, `function.arguments` berupa string JSON mentah). Normalisasi memilih salah satu: `kind="text"` atau `kind="tool_calls"`, tidak pernah keduanya.
- **Konteks percakapan milik aplikasi.** Endpoint chat completions stateless: setiap panggilan mengirim riwayat penuh. Tidak ada penyimpanan percakapan persisten dan tidak ada mekanisme lanjutan (continuation) provider yang diandalkan.
- **Identitas pelanggan terpisah dari argumen model.** `AgentInput` hanya membawa pesan. Identitas pelanggan terautentikasi tidak masuk input agen dan tidak bisa dibentuk oleh keluaran model.

## 4. Desain arsitektur

```
pemanggil aplikasi (lapisan WhatsApp atau API, P2.3+)
        │  AgentInput(list[AgentMessage])
        ▼
AgentOrchestrator ─── AgentMessage(role=system, AGENT_INSTRUCTIONS) + riwayat
        │  internal, tanpa format provider
        ▼
SurplussProvider (adapter) ── HTTP POST /chat/completions (OpenAI-compatible)
        │  AgentResponse
        ▼
kembali ke pemanggil, kind="text" atau kind="tool_calls" (tidak dieksekusi)
```

- Orkestrator: tanpa SQL, tanpa repository, tanpa transaksi, tanpa parsing provider.
- Adapter: tanpa logika bisnis, tanpa instruksi, tanpa orkestrasi.
- Instruksi: data murni (string konstanta), terpisah dari kode.
- Skema: kontrak internal satu-satunya antar komponen.

## 5. Komponen yang dibangun

## 6. Alur eksekusi

1. Aplikasi menerima pesan pengguna dan membangun `AgentInput` (riwayat lengkap, pesan user paling akhir).
2. Orkestrator menerima input, menolak input tidak valid di batas skema (Pydantic).
3. Orkestrator menyiapkan pesan system dari `AGENT_INSTRUCTIONS` dan menyusun ulang daftar pesan lengkap.
4. Adapter mengirim `POST {base_url}/chat/completions` (non-streaming) dengan header `Authorization: Bearer`.
5. LLM memproses permintaan. Router marketplace memilih seller termurah yang sehat.
6. Respons diterima adapter. **Keputusan sukses dilihat dari body, bukan status HTTP** (jebakan terdokumentasi: permintaan lama selalu 200 walau gagal).
7. Respons dinormalkan: `error` dan `choices` dicek, lalu `content` string → `kind="text"`, atau `tool_calls[]` → `kind="tool_calls"`. Bentuk lain → error eksplisit.
8. `AgentResponse` dikembalikan ke pemanggil. Bila `kind="tool_calls"`, pemanggil melaporkannya. Eksekusi menunggu registry P2.2.

## 7. Ringkasan implementasi

- Konfigurasi: `OPENAI_API_KEY`, `OPENAI_MODEL` (wajib, kosong = `AgentConfigurationError` jelas), `OPENAI_BASE_URL` (default URL kanonik terdokumentasi, bisa dioverride env). Nama variabel dipertahankan sesuai permintaan pemilik proyek.
- Klien HTTP: `httpx` sinkron (sudah ada di dependensi), klien per permintaan, timeout baca 120 s dan koneksi 10 s.
- Pengujian: 47 unit test baru (adapter dengan `httpx.MockTransport`, orkestrator dengan provider palsu), 1 smoke test opt-in (`RUN_AGENT_SMOKE=1`), tanpa perlu kunci nyata untuk unit.
- Tanpa migrasi DB, tanpa endpoint baru, tanpa perubahan service bisnis.

## 8. Keputusan teknis

1. **httpx mentah, bukan OpenAI SDK.** Dokumentasi Surplus menyatakan permintaan non-streaming yang berjalan lama mengembalikan HTTP 200 meskipun gagal, dengan error di body, dan secara eksplisit memperingatkan bahwa "memeriksa res.ok atau status 200 memperlakukan generasi gagal sebagai sukses". SDK OpenAI memutuskan sukses dari status. httpx memungkinkan kita bercabang pada body sesuai kontrak terdokumentasi. Bonus: tanpa dependensi baru (httpx sudah terpasang) dan tanpa retry otomatis SDK yang tidak kita inginkan.
2. **Chat Completions, bukan Responses API.** Endpoint `/v1/chat/completions` adalah endpoint primer terdokumentasi ("OpenAI-compatible - works with any client that speaks the OpenAI format"), tool calling terverifikasi pada format ini, dan contoh transkrip multi-turn tool di dokumentasi memakai format ini. Responses API tersedia di provider tetapi tidak dipakai, tidak dipaksakan.
3. **Tanpa `providers/base.py`.** Abstraksi antarmuka dengan satu implementasi = abstraksi tanpa pemakai kedua. Pemisahan provider-orkestrator sudah tercapai lewat kontrak skema internal (`AgentMessage` masuk, `AgentResponse` keluar). Ketika provider kedua benar-benar ada, ekstrak Protocol dari kasus pemakaian kedua itu. (Penyimpangan sadar dari struktur yang diusulkan spec. Alasan: "avoid unnecessary abstraction".)
4. **Model & URL tidak dihardcode di kode.** Model = setting `OPENAI_MODEL` (kosong = error jelas, katalog model hidup dicek via `GET /v1/models`). Base URL = setting dengan default nilai kanonik terdokumentasi, satu-satunya nilai terverifikasi, bisa diganti via env.
5. **Tanpa retry otomatis.** Kegagalan transien (timeout, 503, atau rate limit) sampai ke pemanggil sebagai exception domain. Pemanggil (lapisan API P2.3) yang memutuskan kebijakan retry, sengaja tidak ada backoff gelap di dalam adapter. `AgentRateLimitError` membawa `retry_after` dari header `Retry-After` kalau provider menyediakannya.
6. **Normalisasi gagal eksplisit, tidak dipaksa.** Konten null → invalid, blok konten multimodal → unsupported, tool non-`function` → unsupported, argumen bukan string JSON → invalid. Tidak ada konversi diam-diam ke teks kosong.
7. **Instruksi dalam Bahasa Indonesia.** Agen melayani pelanggan distributor FMCG Indonesia via WhatsApp. Instruksi berbahasa pengguna akhir sejak awal menghindari pergeseran bahasa.

## 10. Risiko dan keterbatasan

- **Kunci belum terpasang.** Happy path ke GLM belum pernah dieksekusi dengan kredensial nyata. Jalankan smoke test begitu `OPENAI_API_KEY` + `OPENAI_MODEL` terisi.
- **Satu panggilan = satu putaran.** Tidak ada loop tool (model meminta tool → hasil dikirim balik → model lanjut). Itu desain P2.2. Orkestrator saat ini hanya melaporkan.
- **Error 402 (tagihan) dipetakan ke `AgentProviderUnavailableError`** dengan `code` asli dipertahankan. Kelas khusus tagihan bisa ditambah kalau API layer ingin pesan berbeda untuk "saldo habis" dan "server sibuk".
- **Timeout klien 120 s** cukup longgar (generasi panjang terdokumentasi). Di belakang WhatsApp webhook nanti perlu batas yang lebih ketat atau mode streaming.
- **Instruksi belum diuji secara perilaku** (hanya keberadaan konten aturan yang dites). Uji perilaku instruksi = evaluasi LLM, di luar P2.1.
- **Tanpa riwayat persisten.** Pemanggil harus menyimpan dan mengirim ulang konteks tiap panggilan (sifat stateless endpoint). Penyimpanan percakapan = milestone tersendiri bila dibutuhkan.

## 11. Pemahaman engineering

Poin terpenting yang didemonstrasikan: **keberhasilan HTTP ≠ keberhasilan bisnis**. Provider ini terdokumentasi mengirim 200 untuk permintaan yang gagal (komitmen status lebih dulu daripada hasil). Satu-satunya kebenaran ada di body: `error` hadir atau `choices` hadir. Kode adapter `surpluss.py::_normalize` membuktikannya:

```python
error = body.get("error")
if error is not None or "choices" not in body:
    self._raise_provider_error(response, body, error)   # gagal, walau status 200
return self._response_from_choices(body)                # sukses, bukan karena 200
```

Contoh konkret satu eksekusi: pengguna kirim `"Berapa harga Aqua 600ml?"`. Pemanggil membangun `AgentInput(messages=[AgentMessage(role="user", content="Berapa harga Aqua 600ml?")])`. Orkestrator menaruh `AGENT_INSTRUCTIONS` sebagai pesan system paling depan, lalu adapter mengirim:

```json
{"model": "glm-5.3", "stream": false, "messages": [
  {"role": "system", "content": "Kamu adalah asisten penjualan ..."},
  {"role": "user", "content": "Berapa harga Aqua 600ml?"}]}
```

Model menjawab (contoh nyata dari sesi pengujian jalur error, dibalik arah sukses): body berisi `choices[0].message.content` = `"Harga sesuai daftar harga Anda."` → `AgentResponse(kind="text", response_id="chatcmpl-...", text="Harga sesuai daftar harga Anda.")`. Kalau model memilih memanggil tool, balasannya berupa `tool_calls` → `AgentResponse(kind="tool_calls", tool_calls=[AgentToolCall(id="call_1", name="product_inquiry", arguments='{"search_term": "Aqua 600ml"}')])`, dan di P2.1 tidak ada yang mengeksekusinya. Keputusan eksekusi menunggu registry tool. Dua jalur itu adalah seluruh produk milestone ini, dan keduanya ternormalisasi ke satu tipe internal sehingga lapisan berikutnya tidak pernah menyentuh format provider.

## 12. Langkah berikutnya (P2.2, Tool Definition & Registry)

Siap dipakai dari P2.2:
- `AgentResponse.kind="tool_calls"` + `AgentToolCall` (id, name, arguments JSON mentah) sudah menjadi kontrak stabil. Registry tinggal memetakan `name` → handler dan memvalidasi `arguments` di batas eksekusi.
- Orkestrator sudah menyusun riwayat penuh, menambahkan pesan `assistant` (berisi tool_calls) dan `tool` (berisi hasil) ke `AgentInput` untuk putaran berikutnya tidak butuh perubahan adapter: format peran `assistant`/`tool` sudah didukung endpoint (terdokumentasi di contoh transkrip multi-turn).
- Error domain siap dipetakan lapisan API. `request_id` tersedia untuk audit.
- `schemas.py::AgentMessage` membatasi peran ke `system|user|assistant`. P2.2 perlu menambahkan peran `tool` (beserta `tool_call_id`), perubahan skema internal kecil yang sudah diantisipasi validasi input (system tetap ditolak dari input).

Terintegrasi menunggu: kunci API asli terpasang di `.env` dan smoke test positif dijalankan sekali.
