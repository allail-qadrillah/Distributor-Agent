# Catatan Engineering, P2.6: Error Handling & Execution Control

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi, verifikasi retry live menunggu kredensial)

## 1. Tujuan

Memberi orkestrator dan adapter provider kendali eksekusi yang terbatas dan teramati: (1) limit eksekusi, maksimum panggilan tool per giliran dan per request penuh, dicek sebelum eksekusi; (2) kebijakan retry transien-saja yang terbatas di batas jaringan provider; (3) record observabilitas per panggilan (correlation id, response_id, nama tool, call id, kategori hasil, durasi, klasifikasi) tanpa membocorkan rahasia.

## 2. Masalah yang diselesaikan

P2.5 loop konvergen tapi tanpa pengendali: model yang meminta 30 panggilan tool dalam satu giliran akan dieksekusi semua (30 kueri DB berurutan dalam satu request pelanggan). Model yang berputar 5 putaran penuh berhenti di exception, tapi putaran ke-4 bisa memuat 20 panggilan sia-sia. Di sisi jaringan, satu 429 atau satu 5xx sesaat membatalkan seluruh percakapan, padahal percobaan ulang 0,5 detik kemudian berhasil. Sebaliknya, retry tanpa batas pada timeout 120 detik akan menggandakan tunggu pelanggan. Tanpa record eksekusi, operator tidak bisa menjawab "tool mana yang lambat dan kategori kegagalan apa yang dominan" tanpa menebak dari log provider.

## 3. Konsep teknis

- **Limit dicek SEBELUM eksekusi, batch tidak pernah parsial.** Giliran model berisi N panggilan: kalau N > limit per giliran, atau sudah-tereksekusi + N > limit total, seluruh batch ditolak (`AgentToolCallLimitError`) tanpa satu pun panggilan jalan. Model tidak pernah melihat "sebagian batch saya berhasil". Hasil parsial adalah jenis kebohongan paling berbahaya bagi agen yang aturannya "jangan klaim berhasil tanpa hasil backend".
- **Retry hanya di batas provider, hanya untuk kegagalan transien.** Percakapan (panggilan completion) murni baca-model, tanpa efek samping bisnis, jadi aman dicoba ulang. Eksekusi tool TIDAK PERNAH di-retry: `create_draft_order` dua kali = dua draft. Transien = `AgentRateLimitError` (hormati `Retry-After`, tunggu > cap → langsung gagal) dan `AgentProviderUnavailableError` (transport, 5xx, atau 503, backoff eksponensial 0,5s → 1,0s). Bukan transien: timeout (120s read sudah terbakar, retry menggandakan tunggu pelanggan), auth, konfigurasi, bentuk respons.
- **Observabilitas = data murni, bukan logging infra.** `AgentRunEvent` (Pydantic) dikumpulkan orkestrator dan dikembalikan lewat `AgentRunResult.events`, field identitas + waktu saja: correlation id (dari `ToolContext.conversation_id`), response_id, nama tool, call id, `ok`, kategori hasil, durasi. Tanpa argumen mentah, tanpa isi pesan, tanpa kredensial. Test menegaskan ketiganya absen dari dump JSON.
- **Klasifikasi error = exception yang menyebar.** Run gagal (provider error, batas putaran, batas panggilan) → exception terklasifikasi naik ke pemanggil. Kelas exception + field-nya (code, request_id, limit_kind) ADALAH klasifikasi yang dicatat pemanggil. Event hanya untuk run yang selesai.

## 4. Desain arsitektur

```
AgentOrchestrator.run
  per putaran:
    clock() → provider.complete(...) → clock()
      ├─ AgentRunEvent(kind="provider_call", response_id, outcome, duration_ms)
      ├─ kind=text   → AgentRunResult(..., events)
      └─ kind=tool_calls:
           _check_call_limits(calls, executed)   ── per_round/total terlampaui
                                                  → AgentToolCallLimitError (batch utuh ditolak)
           per call: clock() → executor.execute(...) → clock()
             ├─ AgentRunEvent(kind="tool_execution", tool_call_id, tool_name, ok, category, duration_ms)
             └─ pesan tool → giliran berikutnya

SurplussProvider.complete (batas jaringan)
  attempt ≤ max_retries (default 2):
    _request → transport error/5xx → sleep(backoff) → ulang
    _normalize → AgentRateLimitError → sleep(Retry-After ≤ cap) → ulang
                 Retry-After > cap → raise sekarang
    timeout / auth / config / bentuk → raise percobaan pertama (permanen)
```

## 6. Alur eksekusi

Skenario 429 lalu sukses:
1. `complete()` → `_request` → respons 429 dengan `Retry-After: 1`.
2. `_normalize` memetakan ke `AgentRateLimitError(retry_after=1.0)`.
3. Attempt 0 < `max_retries` 2, tunggu 1.0 ≤ cap 8.0 → `sleep(1.0)` → attempt 1.
4. `_request` kedua → respons teks normal → `AgentResponse(kind="text")`.
5. Caller hanya melihat satu respons sukses. Test menegaskan tepat 2 request + sleep [1.0].

Skenario batch terlalu besar:
1. Putaran ke-2: model meminta `["c2", "c3"]` sementara 1 call sudah tereksekusi dan `max_tool_calls_total=2`.
2. `_check_call_limits`: 1 + 2 = 3 > 2 → `AgentToolCallLimitError("total", 2, 3)` SEBELUM append giliran assistant/eksekusi.
3. Caller menangkap exception. Transkrip tersimpan pemanggil tetap konsisten (tidak ada pertukaran tool setengah jadi).

## 8. Keputusan teknis dan alasannya

1. **Limit = raise, bukan hasil tool terstruktur.** Konsisten dengan `AgentRoundLimitError` P2.5: batas terlampaui = kegagalan run yang layak dilihat pemanggil, bukan pesan yang dikirim balik ke model. Alasan taktis tambahan: menolak via pesan tool mengundang loop "mengapa panggilan saya gagal" yang justru memakan putaran (tetap dibatasi putaran, tapi dua mekanisme penolakan untuk satu masalah). Konsekuensi: percakapan berhenti pada model menyimpang parah. Itu memang kondisi yang harus dilihat operator.
2. **Total dicek proyeksi (sudah + N), bukan sesudah eksekusi.** Alternatif "eksekusi sampai habis budget lalu tolak sisa" menghasilkan batch parsial, dilarang aturan §3. Ketatnya: proyeksi bisa menolak batch yang sebenarnya masih muat 1–2 call. Diterima demi jaminan tanpa batch parsial.
3. **Retry di provider, bukan orkestrator.** Orkestrator tidak tahu mana panggilan "sama" (tanpa id idempoten). Provider tahu persis bahwa satu `complete()` = satu request HTTP tanpa efek samping. Retry di sana juga otomatis berlaku untuk panggilan pertama (sebelum tool apa pun dieksekusi), momen paling rawan 429 saat warm-up.
4. **Timeout eksplisit TIDAK di-retry.** `httpx.ReadTimeout` ⊂ `TransportError`. Tanpa pemisahan sadar, timeout akan di-retry diam-diam oleh cabang "transien". Read timeout 120s sudah menunggu. Retry = 240s+ total untuk pelanggan WhatsApp. Connect timeout ikut tidak di-retry (kasusnya jarang, harga kesederhanaan satu cabang, naikkan kalau log menunjukkan kebutuhan).
5. **`Retry-After` > cap (8s) → gagal sekarang.** Menunggu 60 detik untuk pelanggan obrolan lebih buruk dari gagal. Pemanggil bisa memilih kebijakan sendiri (antre ulang, maaf). `retry_after=None` → backoff eksponensial default.
6. **Event sebagai data di `AgentRunResult`, bukan `logging`.** Proyek belum punya infra logging. `logging` tanpa konfigurasi = record hilang ke stderr default. Data murni bisa dipersist, diuji, dan dipindahkan ke logger apa pun saat lapisan aplikasi ada. Kompromi: event run yang berakhir exception tidak dikembalikan. Klasifikasinya sudah dibawa exception itu sendiri (didokumentasikan §10).
7. **Konfigurasi via parameter konstruktor (default: 5 putaran, 8 per giliran, 16 total, 2 retry).** Bukan env atau `Settings`. File `config.py` punya perubahan pemilik yang belum di-commit dan baris CRLF. Env wiring menyusul bersama lapisan aplikasi yang benar-benar membaca env, saat konteks pemakai sudah jelas. Konstruktor = titik injeksi yang sudah ada dan teruji.
8. **Backoff eksponensial deterministik tanpa jitter.** Test bisa menegaskan [0.5, 1.0] persis. Jitter bernilai saat banyak worker berbagi limit yang sama. Belum ada worker pool di fase ini (ponytail: tambah `random.uniform(0, delay)` saat konkurensi nyata ada).

## 10. Risiko dan keterbatasan

- **Event hilang saat run gagal** (provider error atau limit exception): tidak dikembalikan maupun dilog. Mitigasi sekarang: exception membawa klasifikasi lengkap. Kalau audit gagal-run perlu event, naikkan event ke pemanggil lewat callback. Catat masalahnya dulu, belum ada pemakainya.
- **Limit dan konfigurasi belum dari env**, hanya default konstruktor. Aplikasi production harus menyuntik eksplisit (mis. 3 per giliran dan 6 total untuk kanal WhatsApp yang sensitif latensi). Didokumentasikan di DECISIONS.
- **Retry provider menaikkan latensi paling buruk ±9,5s** (2 backoff: 0.5+1.0, atau tunggu rate-limit ≤ 8s), masih dalam batas wajar obrolan. Cap dan max_retries parameter injeksi kalau kanal butuh lebih ketat.
- **Tanpa circuit breaker global**, provider mati lama = tiap request membayar 2 retry. Fase 2 single-tenant per sesi. Circuit breaker menyusul bersama lapisan aplikasi berkonkurensi.
- **Durasi tool event mencakup seluruh eksekusi service** (termasuk koneksi DB), granularitas query tunggal tidak dibutuhkan untuk diagnosis agen.

## 11. Pemahaman engineering

Pembelajaran inti: **retry adalah keputusan keamanan, bukan keputusan kenyamanan**. Aturan penentu: "apakah percobaan ulang entitas ini bisa mengubah keadaan bisnis?" Panggilan completion: tidak, model diberi input sama, jawaban mungkin beda, tapi tidak ada draft dibuat, tidak ada stok direservasi. Eksepsi `AgentProviderUnavailableError` dan `AgentRateLimitError` hanya boleh memicu retry karena keduanya naik DARI panggilan completion. Eksekusi tool: ya, `create_draft_order` idempoten-palsu (draft baru tiap panggilan), `confirm_order` terjaga status tapi tetap transaksi nyata. Maka retry dipisahkan persis di batas itu: dalam provider, sebelum tool mana pun jalan.

Data observabilitas memakai disiplin yang sama dengan `ToolResult` (P2.4): **kegagalan adalah data**, tapi di sini datanya dibatasi identitas+waktu. Test `test_events_carry_no_secrets_or_raw_arguments` menegaskan dump JSON event bebas `search_term`, `arguments`, dan `customer`. Record bisa masuk log umum tanpa sanitasi tambahan.

Contoh record yang dihasilkan satu run satu-putaran-tool:

```python
[AgentRunEvent(kind="provider_call", correlation_id="wa-9", response_id="chatcmpl-2",
               outcome="tool_calls", duration_ms=500),
 AgentRunEvent(kind="tool_execution", correlation_id="wa-9", tool_call_id="call_1",
               tool_name="search_products", ok=True, category=None, duration_ms=500),
 AgentRunEvent(kind="provider_call", correlation_id="wa-9", response_id="chatcmpl-1",
               outcome="text", duration_ms=500)]
```

Operator membaca: percakapan wa-9 → 2 panggilan model (503ms, 502ms), 1 tool sukses (498ms). Kategori dominan bisa dihitung dengan group-by biasa.

## 12. Langkah berikutnya (P2.7, Order Tool Integration & Safety)

- Uji alur pesanan penuh LEWAT agen: pencarian → draft → klarifikasi → persetujuan eksplisit (`with_confirm_order_approval()`) → konfirmasi sukses; dan jalur penolakan: tanpa approval, draft milik pelanggan lain, stok kurang, limit kredit.
- Ambiguitas multi-kandidat: hasil `search_products` > 1 kandidat → agen harus bertanya, bukan memilih, verifikasi perilaku di lapisan orkestrator (approval & ambiguitas = keputusan logika aplikasi, bukan model).
- Test siklus hidup penuh dengan `FakeProvider` berurutan + `FakeToolExecutor` dan service fake, plus test provider-integrasi bentuk pesan konfirmasi.
