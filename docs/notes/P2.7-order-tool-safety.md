# Catatan Engineering, P2.7: Order Tool Integration & Safety

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi, jalur model nyata menunggu kredensial)

## 1. Tujuan

Membuktikan keamanan alur pesanan END-TO-END lewat agen: tumpukan NYATA (orkestrator → executor → handler → service) dengan hanya provider yang di-script dan database yang di-fake. Skenario: siklus hidup penuh (cari → draft → persetujuan eksplisit → konfirmasi), penolakan tanpa approval, draft milik pelanggan lain, order_id karangan, kegagalan bisnis (stok kurang), ambiguitas multi-kandidat, dan penyelundupan identitas dan harga dari model.

## 2. Masalah yang diselesaikan

P2.2–P2.6 menguji tiap lapisan terpisah: handler diuji dengan args instan, orkestrator diuji dengan executor fake. Celah verifikasi: tidak ada test yang membuktikan lapisan-lapisan itu BEKERJA SAMA dengan benar, bahwa hasil `confirm_order` benar-benar sampai ke model SEBELUM model menjawab "terkonfirmasi", bahwa transkrip yang dipersist antar-run mempertahankan pertukaran tool, bahwa approval yang diberikan logika aplikasi benar-benar satu-satunya kunci konfirmasi pada jalur lengkap. Tanpa test siklus hidup, regresi integrasi antar-lapisan (mis. refactor signature, perubahan urutan pesan) hanya terlihat saat percakapan nyata.

## 3. Konsep teknis

- **Uji jalur nyata, fake hanya di tepi.** `ScriptedProvider` menggantikan model (respons di-script per skenario, semua pesan yang dilihat model direkam). `FakeProductInquiryService` dan `FakeOrderService` menggantikan DB. Di antaranya: `AgentOrchestrator` asli, `build_tool_executor` asli, handler asli, validasi argumen asli, `ToolContext` asli. Kegagalan test = kegagalan wiring nyata.
- **Percakapan lintas-run dengan replay transkrip.** Siklus hidup penuh = TIGA `run()` terpisah (harga → pesan → konfirmasi), tiap run membawa `transcript` run sebelumnya + pesan user baru, persis pola pemakaian lapisan aplikasi. Ini juga menguji replay P2.5 di jalur bisnis nyata, bukan hanya sintetis.
- **Verifikasi "model melihat sebelum menjawab".** Test membaca balik pesan tool yang diterima provider (`provider.seen[n]`): jawaban teks model tentang konfirmasi HANYA sah kalau sebelumnya provider menerima `ToolResult(ok=True, status="confirmed")`. Urutan kausal ini inti aturan "jangan klaim berhasil tanpa hasil backend".
- **Ambiguitas = kelengkapan data + nol aksi.** Hasil pencarian 2 kandidat: test menegaskan model menerima KEDUA kandidat utuh (cukup untuk bertanya, tak bisa mengarang) dan `create_draft_order` tidak pernah terpanggil dari kecocokan ambigu.
- **Penyelundupan tetap mustahil di jalur lengkap.** Argumen karangan (`customer_id`, `items_prices`) ditolak di batas, service tidak pernah melihatnya. Field yang diselundup disebut nama di detail error.

## 6. Alur eksekusi

Siklus hidup penuh (test 1):
1. **Run 1**, user "berapa harga aqua?": provider → `search_products` → `ToolResult(products[AQUA600 Rp150])` → provider (menerima hasil) → teks. Transkrip run 1 = `[user, assistant(tc), tool]`.
2. **Run 2**, input = transkrip run 1 + "pesan 10 ya": provider → `create_draft_order` → handler membangun `OrderCreate(customer_id=DARI KONTEKS)` → draft → teks.
3. **Run 3**, input = transkrip run 2 + "ya, konfirmasi"; KONTEKS approved (logika aplikasi memanggil `with_confirm_order_approval()`): provider → `confirm_order` → handler cek approval ✓ → `get_order` ownership ✓ → `confirm_order` service → `ToolResult(ok, status=confirmed)` → provider menerima → teks "terkonfirmasi".
4. Test membaca `provider.seen[5]`: panggilan provider setelah hasil konfirmasi memuat JSON dengan `ok: true, status: "confirmed"`, bukti kausal model menjawab SETELAH backend berhasil.

## 8. Keputusan teknis dan alasannya

1. **Test integrasi, bukan kode baru.** Perilaku yang diminta milestone (approval flow, ambiguitas, siklus hidup) sudah mekanis di P2.3–P2.6. Menambah kode berarti menduplikasi penjaga. Yang belum ada: bukti lapisan bekerja bersama, itu yang dibangun. YAGNI terpenuhi.
2. **Provider di-script per skenario (bukan executor).** Meng-fake executor akan mengulang test P2.5 tanpa menyentuh handler/guard sama sekali. Script provider memaksa alur melewati SEMUA lapisan nyata di antara.
3. **Direkamnya pesan yang dilihat provider (`seen[]`).** Kebenaran kausal "model menjawab terkonfirmasi hanya setelah melihat ok=true" tidak bisa diverifikasi dari hasil akhir saja, harus dari urutan pesan pada kabel. Membaca balik `seen[n]` menjadikan urutan itu assertable.
4. **Ambiguitas diuji dari sisi data, bukan sisi kepatuhan model.** "Model harus bertanya, bukan memilih" adalah perilaku model, diuji lewat smoke test hidup (P2.8, setelah kredensial tersedia). Yang dijamin kode: kedua kandidat terkirim utuh + tidak ada jalur otomatis membuat draft dari hasil ambigu (tool description melarang, test menegaskan bagian mekanisnya).
5. **Skenario penyelundupan end-to-end** meski sudah ada test unit P2.3. Satu test di jalur lengkap menutup risiko "lapisan terpisah aman, integrasinya bocor". Harganya murah (satu fungsi) dan menjadi regresi wiring.
6. **Fake service mandiri di file test** (bukan diimpor dari file test lain). Test integrasi harus bisa dibaca berdiri sendiri: skenario, fake, dan asersi dalam satu tempat. Duplikasi kecil fake diterima demi itu.

## 10. Risiko dan keterbatasan

- **Kepatuhan model tidak diuji di sini**, deskripsi tool + instruksi mengarahkan perilaku (bertanya saat ambigu, minta persetujuan), tapi hanya smoke test hidup yang membuktikan model mengikuti. Mekanisme penjaga tetap bekerja apa pun perilaku model: itulah yang diuji.
- **Deteksi persetujuan eksplisit disimulasikan** (`_context(approved=True)`), logika nyata ("ya, konfirmasi" → approval) milik lapisan kanal (fase berikutnya). P2.7 membuktikan: satu-satunya jalan konfirmasi = konteks approved + draft milik sendiri.
- **Transkrip lintas-run diuji 3 run.** Percakapan sangat panjang (puluhan run) tidak bersimulasi. Batas konteks model 1.048.576 token membuatnya tidak relevan fase ini.
- **Fake service tidak mensimulasikan konkurensi**, dua request paralel pada draft sama tidak diuji (race dijaga `confirm_order` milik service, sudah teruji di test service sendiri).

## 11. Pemahaman engineering

Pembelajaran inti: **test integrasi terbaik adalah yang tidak mengubah kode produksi**. Milestone ini nol diff di `src/`. Semua yang gagal di sini pasti kegagalan nyata pada wiring yang pelanggan akan alami. Bandingkan tiga lapisan verifikasi yang kini menumpuk:

```python
# P2.4 (unit): handler menolak tanpa approval, orders.get_order_ids == []
# P2.5 (unit): loop memasangkan tiap tool_call_id dengan tepat satu hasil
# P2.7 (integrasi): penolakan itu BENAR-BENAR dilihat model sebelum menjawab,
#   provider.seen[1] memuat {"ok": false, "error": {"code": "unauthorized", ...}}
#   dan final_text = "Mohon persetujuan Anda dulu sebelum konfirmasi."
```

Rantai kausal lengkap: pelanggan bilang "konfirmasi" → logika aplikasi BELUM memberi approval → model (apa pun niatnya) memanggil `confirm_order` → handler menolak SEBELUM service → model membaca penolakan → model meminta persetujuan. Tidak ada satu titik pun di rantai itu yang memercayai model. Persetujuan pelanggan menjadi konfirmasi pesanan hanya melalui keputusan eksplisit kode aplikasi. Model diberi hak bicara, bukan hak tanda tangan.
