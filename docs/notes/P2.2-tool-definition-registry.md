# Catatan Engineering, P2.2: Tool Definition & Registry

Tanggal: 2026-11-17 · Status: selesai dan terverifikasi (unit + regresi, verifikasi model via katalog live, panggilan tool live menunggu kredensial)

## 1. Tujuan

Menentukan tiga tool yang tersedia bagi model (`search_products`, `create_draft_order`, `confirm_order`) dalam format function calling OpenAI-compatible yang didukung provider, dan membangun registry yang memetakan nama tool ke definisinya dengan penjaga ketat: nama duplikat ditolak, nama tak dikenal ditolak. Eksekusi tool belum ada. Milestone ini hanya definisi + registry + jalur pengiriman definisi ke provider.

## 2. Masalah yang diselesaikan

P2.1 bisa mendeteksi `kind="tool_calls"` tetapi tidak ada daftar tool apa pun yang dikirim ke model, sehingga model tidak pernah bisa meminta tool secara terstruktur. Tanpa registry terpusat, pemetaan nama→definisi akan tercecer di orkestrator dan rawan duplikat senyap. Tanpa invariant keamanan pada skema, model bisa "membantu" dengan mengirim `customer_id` atau harga dalam argumen, dua hal yang tidak boleh berasal dari model.

## 3. Konsep teknis

- **Function calling format OpenAI.** Provider (Surpluss Intelligence) menormalkan semua format tool ke satu bentuk kanonik dan meneruskan format standar OpenAI tanpa perubahan (dok "Tool normalization"): `{"type": "function", "function": {name, description, parameters}}`. Non-function tool dibuang sebelum diteruskan. Definisi kita memakai format standar itu apa adanya.
- **JSON Schema parameter ditulis tangan, inline.** Tanpa `$ref`/`$defs`, tidak ada risiko resolusi referensi di sisi provider, dan setiap konstrain (`minItems`, `minimum`, `additionalProperties: false`) terbaca tepat di samping deskripsinya. Validasi argumen aktual dengan Pydantic menyusul di P2.3 di batas eksekusi.
- **Invariant keamanan dibak ke dalam data.** Tidak ada definisi yang memuat `customer_id` (identitas dari konteks terpercaya, P2.3), tidak ada field harga (harga satuan ditetapkan backend dari daftar harga), dan `confirm_order` hanya menerima `order_id`, persetujuan eksplisit tidak pernah menjadi argumen model.
- **Registry = satu sumber kebenaran tool yang ada.** Duplikat = error pemrograman (gagal keras saat startup, tidak menimpa senyap). Nama tak dikenal = error model (nanti dikembalikan ke model sebagai hasil tool terstruktur agar model bisa pulih, P2.5 dan P2.6).

## 4. Desain arsitektur

```
build_default_registry() ── ToolRegistry ── openai_tools() ── list[dict] (wire)
        │                        │
SEARCH_PRODUCTS_TOOL      get(name) → ToolDefinition   (unknown → UnknownToolError)
CREATE_DRAFT_ORDER_TOOL   register(tool)               (duplikat → DuplicateToolError)
CONFIRM_ORDER_TOOL
```

- `definitions.py` = data murni (`ToolDefinition` frozen dataclass, tervalidasi saat konstruksi).
- `registry.py` = struktur (peta nama→definisi + penjaga + emisi wire) + pabrik registry bawaan.
- `surpluss.py::complete(messages, tools=None)` = satu-satunya titik definisi menyentuh kabel provider. `tools` disertakan di payload hanya bila diberikan (default tanpa tool, model menjawab teks biasa).
- Handler sengaja **belum** ada. Tool tidak dianggap dapat dieksekusi hanya karena skemanya ada (jalur eksekusi + otorisasi menyusul di P2.4).

## 6. Alur eksekusi

1. (P2.5 nanti) Orkestrator memanggil `ToolRegistry.openai_tools()` → daftar spec wire.
2. Orkestrator meneruskannya ke `provider.complete(messages, tools=specs)`.
3. Adapter menyusun payload `{"model", "stream": false, "messages", "tools"}`. Tanpa argumen `tools`, kunci tidak dikirim sama sekali.
4. Provider menormalkan (format standar kita diteruskan apa adanya) dan mengirim ke model.
5. Model menjawab teks atau `tool_calls`. Adapter sudah menormalkannya sejak P2.1 (`AgentToolCall` id/name/arguments JSON mentah).
6. Nama tool dari `AgentToolCall.name` nanti dicek ke registry: ada → P2.3 validasi argumen. Tidak ada → `UnknownToolError`.

## 8. Keputusan teknis dan alasannya

1. **JSON Schema ditulis tangan, bukan hasil `model_json_schema()` Pydantic.** Pydantic memancarkan `$defs`/`ref` untuk model bersarang (item pesanan) dan menambahkan `format: "uuid"` + `title`, tiga sumber ketidakpastian kompatibilitas lintas provider sekaligus. Ditulis tangan: skema datar, deskripsi presisi, nol risiko referensi. Konsekuensi: bentuk argumen terdefinisi di dua tempat (skema wire di sini, model Pydantic di P2.3). Sinkronnya dijaga test yang menegaskan properti skema cocok dengan kontrak service (`OrderCreate`, `ProductInquiryRequest`) dan, mulai P2.3, test yang menegaskan field model Pydantic sama dengan properti skema.
2. **Registry tanpa slot handler di P2.2.** Menyimpan `handler: Callable | None` sekarang berarti menebak tanda tangan handler sebelum konteks terpercaya (P2.3) dan lapisan eksekusi (P2.4) ada. P2.4 memperluas registry dengan handler nyata saat kontraknya sudah diketahui. Penundaan ini eksplisit di docstring registry.
3. **`additionalProperties: false` di semua level skema.** Cermin dari `BaseSchema` proyek (`extra="forbid"`): field tak dikenal dari model ditolak, bukan diabaikan senyap. Strictness ganda ini (skema wire + Pydantic P2.3) menjaga batas kepercayaan.
4. **Deskripsi tool Bahasa Indonesia, identifier Inggris.** Model melayani pelanggan Indonesia dan instruksi sistem berbahasa Indonesia. Deskripsi sewarna mengurangi pergeseran bahasa. Field name (`search_term`, `product_id`) tetap Inggris, konsisten dengan kontrak service.
5. **Model terpilih = `deepseek-v4.1-flash-1017` (per tugas induk).** Diverifikasi live di `GET /v1/models`: ada, `tools` didukung, konteks 1.048.576. Ini nilai konfigurasi (`OPENAI_MODEL`), bukan kode, kode tetap agnostik model. Hanya komentar contoh `config.py` dan `.env.example` yang diperbarui. Catatan: P2.1 memakai contoh `glm-5.3`. Keduanya valid di katalog. Pemilihan final milik pemilik proyek via `.env`.
6. **`tool_choice` tidak dikirim.** Default provider (auto) sudah sesuai alur "model memilih tool secara mandiri". Aplikasi tidak pernah memaksa tool tertentu. Mengirimnya berarti parameter tanpa pemakai.

Kemampuan "definisi dapat dikirim ke model" diverifikasi pada lapisan payload adapter, bukan pada percakapan hidup.

## 10. Risiko dan keterbatasan

- **Dua representasi bentuk argumen** (skema wire vs model Pydantic P2.3) bisa bergeser. Mitigasi: test sinkronisasi per tool. Tambahkan di P2.3 bersama modelnya.
- **Tool call live belum pernah diterima dari model nyata.** Format respons sudah terdokumentasi + adapter sudah menormalkannya (unit test mock sejak P2.1), tapi kecenderungan model (mis. kerapian argumen JSON) baru terlihat saat smoke test hidup.
- **Deskripsi tool belum diuji perilaku** (apakah model benar memilih `search_products` sebelum menyebut harga). Itu evaluasi LLM, menunggu kredensial.
- **Order tools belum bisa dieksekusi.** Registry tanpa handler. `openai_tools()` masih akan mengirim ketiga definisi begitu orkestrator P2.5 mulai menggunakannya. Pastikan handler P2.4 sudah lulus uji sebelum orkestrator mengaktifkan pengiriman (urutan milestone sudah menjamin ini).

## 11. Pemahaman engineering

Pembelajaran inti: **batas kepercayaan paling murah ditegakkan pada skema, bukan pada kode pemeriksa**. Menolak `customer_id` dari model bisa dilakukan dengan validasi runtime di handler (P2.3 memang akan memvalidasi lagi), tapi argumen yang *tidak pernah diminta* tidak akan pernah dikirim. Model mengisi formulir yang kita berikan. `CREATE_DRAFT_ORDER_TOOL.parameters` tidak memuat field harga dan `CONFIRM_ORDER_TOOL.parameters` hanya `order_id`. Deskripsi masing-masing menyatakan aturan itu dalam bahasa yang model baca. Dua lapis (data + validasi) mengalah satu lapis (validasi saja).

Contoh konkret wire yang dihasilkan `build_default_registry().openai_tools()[0]`:

```json
{
  "type": "function",
  "function": {
    "name": "search_products",
    "description": "Cari produk berdasarkan istilah pencarian ... Identitas pelanggan TIDAK dikirim sebagai argumen; sistem menentukannya secara otomatis.",
    "parameters": {
      "type": "object",
      "properties": {
        "search_term": {"type": "string", "description": "Istilah pencarian: nama produk, alias, atau SKU, misalnya 'Aqua 600 ml' atau 'AQUA600'."}
      },
      "required": ["search_term"],
      "additionalProperties": false
    }
  }
}
```

Objek persis inilah yang dimasukkan adapter ke payload `POST /chat/completions` bila orkestrator memanggil `complete(messages, tools=...)`. Teruji oleh `test_tools_included_in_payload_when_provided`.

## 12. Langkah berikutnya (P2.3, Customer Context & Argument Validation)

- Definisikan konteks eksekusi terpercaya: `customer_id` terautentikasi + metadata percakapan + penanda persetujuan eksplisit konfirmasi, semua dari logika aplikasi, bukan dari argumen model.
- Model Pydantic v2 untuk argumen tiap tool (`SearchProductsArgs`, `CreateDraftOrderArgs`, `ConfirmOrderArgs`), parsing string JSON mentah `AgentToolCall.arguments` dengan penolakan: JSON rusak, field wajib hilang, tipe salah, field tak dikenal (`extra="forbid"`), UUID salah bentuk, kuantitas ≤ 0.
- Pisahkan empat konsep: argumen mentah model → argumen tervalidasi → konteks terpercaya → permintaan service internal.
- Test sinkronisasi skema wire ↔ model Pydantic per tool (menutup risiko dobel representasi di atas).
